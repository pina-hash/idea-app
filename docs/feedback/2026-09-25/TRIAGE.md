## Findings by cluster

### Cluster: scroll

#### R29 (primary), R07 (probable same cause) -- bug-confirmed (size S, P0-broken-in-class)
**Ask.** The page randomly cannot scroll on many different pages, a refresh fixes it, and it started after a recent update (R29). Every tournament page could not scroll on a 5120x2626 screen (R07).

**Evidence.** There is one sitewide scroll lock that nothing scopes or undoes: src/lib/ideacad/app/IdeaCadApp.svelte:429 `:global(html), :global(body) { width: 100%; height: 100%; overflow: hidden; }` (plus :430 `:global(body){margin:0}`). The same pattern is in src/routes/ideacad/preview/+page.svelte:9-10. Svelte compiles a `:global()` rule into the route's CSS chunk with nothing scoping it. On a client-side navigation SvelteKit adds that chunk's stylesheet to <head> and never removes it when you leave the route. So after one visit to /ideacad (the launcher card is src/lib/portal-apps.ts:94-98, href '/ideacad', a normal client-side link), every later page in the same tab has html/body stuck at `overflow:hidden; height:100%`. Content is cut off at the viewport and the scrollbar is gone. A full reload drops the stylesheet, which matches the report's 'refresh fixes it'. It looks random because it depends on whether IdeaCAD was opened earlier in that tab. A DeployWatch reload (src/lib/shell/DeployWatch.svelte) also clears it, which makes it look more random still. Git history: the rule has been on main since 636fb6e (2026-09-14). The heavy IdeaCAD use and the IdeaCAD overnight merges (3b60bfb..3384940, 2026-09-23) fit 'after the last update'. The only author is Mr. Pina, who was working in IdeaCAD a lot (R34 was filed from /ideacad). I checked the rest of the tree for the same failure: this is the ONLY `:global(html|body)` rule outside src/routes/dev. Every room stylesheet (classroom.css:71/95, notebook-theme.css:144/153, forge.css:171/179, TvStage.svelte:527, ProjectorView.svelte:269) is correctly scoped with `body:has(.<room>)`, so it switches off once the room is gone. No imported .css file has a bare html/body rule. Tournaments has no lock of its own: src/routes/tournaments/+layout.svelte is a plain wrapper, tournaments-theme.css:151-157 `.tnm-shell` is only `position:relative; min-height:100vh`, and TvStage's `body:has(.tv.fixed)` is live-scoped, so it clears when the TV stage unmounts. On the 5120x2626 screen the tournament page may also just fit in the window, but 'cannot scroll' on every tournament page is exactly the leak's signature. Lower-probability second mechanism: two inline body locks, ContentComposer.svelte:1233-1281 and PathwayPicker.svelte:152-156, each save `previous` and restore it. If they overlap and tear down in non-LIFO order, the restore leaks `hidden` (A locks, B locks with previous='hidden', A restores '', B restores 'hidden'). They rarely co-occur (PathwayPicker is the home-page pathway sheet, ContentComposer is the classroom editor). Not suspects: Lightbox is a native showModal dialog (Lightbox.svelte:306-309) and does not lock scroll; CommandPalette, SpotlightTour, ClassroomTour and DeployWatch only preventDefault keys, and SpotlightTour's window scroll listener is passive (SpotlightTour.svelte:191); `.cr-app` (split.css:255-290) is classroom-only and scrolls inside its panes.

**Root cause / approach.** Root cause: the sitewide `:global(html),:global(body){overflow:hidden;height:100%}` in IdeaCadApp stays in effect after you leave /ideacad by a client-side link. Fix: scope the lock to the room with the repo's existing convention, e.g. `:global(html:has(.app-shell)), :global(body:has(.app-shell)) {...}`. Better, give IdeaCAD's root a unique class such as `.ic-app-shell`, because `.app-shell` is generic. Scope the margin rule the same way. Apply the same fix to ideacad/preview/+page.svelte. The alternative is to make `.app-shell` `position:fixed; inset:0` (as `.direct-frame` already is at :428) and drop the html/body rules entirely. Leave the /dev/ideacad-* harness copies alone or fix them to match; they are dev-only. Add a silent-regression guard: a source sweep test (node project) that fails on any `:global(html)`/`:global(body)`/`:global(:root)` rule in a non-dev .svelte file that is not inside a `:has(` selector, with a positive control fixture. This is exactly the 'regression would be silent' class CLAUDE.md allows a test for. Optional hardening in the same bundle: replace the two ad-hoc `document.body.style.overflow` locks with one ref-counted `$lib/shell/scroll-lock.ts` (acquire returns a release; lock while count>0), so an out-of-order teardown cannot leak. Reproduce in a /dev harness: run `npm run dev`, open /dev/ideacad-app (it mounts the real IdeaCadApp), then navigate CLIENT-SIDE (an <a> click or `goto`, NOT a typed URL) to a long page such as /dev/tournaments. Read `getComputedStyle(document.documentElement).overflow` and `document.body` height: before the fix they read 'hidden' and 100%, with `scrollHeight > innerHeight` and `window.scrollTo(0,9999)` leaving `scrollY` at 0. After a hard reload the same page scrolls. Put this in a browser-verify route spec (e.g. tools/browser-verify/routes/ideacad-leaves-no-scroll-lock.mjs) with `--break` coverage, measured at 375 and 1440, and also at 5120x2626 on /dev/tournaments to settle R07's viewport independently. Dev mode shows the leak too (Vite-injected style tags persist across navigation), so the harness reproduces it without a production build.

### Cluster: status

#### R14 -- bug-confirmed (size S, P0-broken-in-class)
**Ask.** A student's My Classes card and To-do chip say "1 missing" for a class, but the class page itself shows nothing missing.

**Evidence.** The Missing predicate is shared, but the two surfaces feed it DIFFERENT check-in sets. buildTodo (src/lib/classroom/todo.ts:184-212) counts every check-in from loadClassroomWork (src/lib/classroom/student-work.ts:405-420), including check-ins attached to an item through 0120's item_id. ClassView only counts streamCheckIns (src/lib/classroom/ClassView.svelte:428 and :471-473), and that function drops every attached check-in (src/lib/classroom/class-check-ins.ts:676-678: `filter((c) => !c.item_id)`). The comment at ClassView.svelte:628-631 says an attached check-in "renders on that item". That is true only on the ITEM PAGE (checkInsForItem is used in ItemDetail and the item route, never in ClassView), so the class list shows no row, no chip and no count for it. Result: a past-day, unfiled check-in hanging off an item (usually the day's MATERIAL) counts as "1 missing" on /classroom, the home To-do door and /classroom/todo, while the class page's Missing chip reads 0 and no row shows it. The screenshot matches (the IDEA209H card and the To-do header both read "1 missing"). This also makes false CLAUDE.md's claim that the counts "cannot disagree": the predicate is one function, but its inputs are not the same set. Repro: in /dev/classroom (or a seeded DB), post a material, attach a check-in dated yesterday, file no entry as the student, then compare the /classroom card with the /classroom/<id> Missing chip. Also note: once an item's own assignment is graded, the row reads Done while the missing check-in stays invisible.

**Root cause / approach.** Make the class page count and show attached check-ins. Pass ALL of the student's check-ins (not just streamCheckIns) into standingCounts for the chips, and put a check-in chip on the item row it hangs off (reuse checkInStatusLabel/checkInTone, colour plus word). Also make the Missing/To do/Done filter keep an item whose attached check-in matches, so the row the count points to is actually on screen. Do not drop attached check-ins from the to-do instead; that would hide real owed notebook work. No migration.

**Migration.** no, it is client-side only; the item_id column already exists (0120).

**Files.** `src/lib/classroom/ClassView.svelte`, `src/lib/classroom/class-check-ins.ts`, `src/lib/classroom/todo.ts`, `src/lib/classroom/classroom.ts`, `src/lib/classroom/student-work.ts`
