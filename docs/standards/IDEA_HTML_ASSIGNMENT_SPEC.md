## 1. What an HTML assignment is

A **ported HTML assignment** is an entire self-contained HTML document -- markup, styles
and script, all inline -- that a student works inside. It is uploaded whole by an
instructor, stored verbatim, and served from a second origin inside a sandboxed iframe.
Nothing rewrites a stored byte at any point: what a reviewer reads is what executes.

It exists because IDEA already has a shelf of them. `src/lib/legacy/assignments/` holds
twelve authored HTML worksheets that students are working in today, each with its own
widgets, counters, demos and print rules. Rebuilding one as a `schemaVersion: 1`
interactive spec means re-authoring the whole document into a block vocabulary that
cannot express what it does. Porting it means adding a manifest and deleting four
functions.

### 1.1 How it differs from a `schemaVersion: 1` spec

| | `schemaVersion: 1` spec (0086) | HTML assignment (0195) |
|---|---|---|
| What is stored | A JSON DESCRIPTION of a worksheet, in `classroom_assignment_specs` | The WORKSHEET, in `classroom_html_assignments.document` |
| Who renders it | `AssignmentEngine.svelte`, from the spec | The document itself, inside an iframe |
| Where it runs | The portal origin, in the page | A second origin, in an opaque-origin sandbox |
| Block vocabulary | `instructions`, `textField`, `table`, `imageZone`, `checklist`, `calc` | `text`, `longText`, `checkbox`, `radio`, `image`, `table` |
| Authoring | Written as a spec | Written as HTML; the manifest is added |
| Editing after import | Edit the spec in place | RE-UPLOAD. There is no in-place editing of a document we do not parse |
| Rubric | Authored, or generated by `rubricFromSpec` | Generated by `manifestToRubric` at every upload |
| Discriminator | `classroom_items.assignment_schema_version` is NULL or 1 | it is `3` |

**`kind` STAYS THE THREE-VALUE CHECK.** An HTML assignment IS an assignment: it has
points, a due date, a rubric, a submission and a grade. A fourth `kind` would fork every
list, feed query, export and policy that names the set in order to record a fact about
how the item RENDERS. The schema-version column is that fact, in one nullable integer,
and `$lib/classroom/html-assignment/mount.ts` is the ONE place the question is asked.

**AN ANSWER IS AN ORDINARY `classroom_responses` ROW.** That is the whole reason the
feature is additive: grading, extra credit, bulk grading, the Grades tab and the FACTS
export read `(item_id, student_email, block_id)` and cannot tell an HTML assignment from
a spec-driven one. Nothing in 0195 moves an answer. See section 9 for the write gate
that means no answer can currently be written at all.

**THE SCHEMA VERSION IS `3` AND THERE IS NO 2.** `HTML_MANIFEST_SCHEMA_VERSION`,
`HX_SCHEMA_VERSION` and `HTML_ASSIGNMENT_SCHEMA_VERSION` are three names for the one
number, in `manifest.ts`, `bridge.ts` and `mount.ts` respectively, and the CHECK on
`classroom_items.assignment_schema_version` admits `null`, `1` and `3`.

## 2. Decisions locked before the build

| Decision | Choice |
|---|---|
| Serving origin | A second host, `sandbox.ideabosco.com`, configured by `PUBLIC_HX_SANDBOX_ORIGIN`. Unset means any host, which is dev and preview. |
| Sandbox flags | `allow-scripts`, alone. `allow-same-origin` must never join it. |
| Sandbox delivery | BOTH the iframe attribute and the CSP `sandbox` directive, from one constant. |
| Network reach | None. `connect-src 'none'`, `form-action 'none'`, no host on any fetching directive. |
| Who may upload | Section 8. Two gates: the permanent `_classroom_manages_item`, and an admin-only SEASON gate. |
| Editing a document | Re-upload. Every upload snapshots the displaced document as a revision. |
| The serving handle | `document_id`, its own uuid, NOT the item id, stable across revisions. |
| Answer storage | `classroom_responses`, unchanged, through `classroom_save_response`. |
| Rubric | Generated from the manifest at import and at every re-upload. Never hand-authored beside a document. |
| Image bytes | Frame to parent only. What returns is a URL. |
| Submit | A PARENT control in parent chrome, never inside the document. |

## 3. Explicitly out of scope

Stated so absence is not read as oversight.

- **In-place editing of a stored document.** We do not parse it and must not rewrite it,
  so there is nothing to edit. Re-upload is the entire edit story.
- **A student authoring an HTML assignment.** Upload is instructor-and-admin only.
- **Any network reach from inside a document.** No CDN, no fonts host, no `fetch`. This
  is the deliberate difference from a Foundry bundle, whose build contract promises one.
- **A second write path for HTML answers.** A private RPC would be a second definition
  of what an answer is. See section 9.
- **An approval gate.** A manifest has no `approvalGate`, so `HX_REFUSALS` carries no
  `approval_pending` branch: there is no path that reaches it.
- **`window.print()` from inside a document.** Refused by the sandbox without
  `allow-modals`; Chromium logs the refusal and `print()` returns without throwing, so a
  Print control in a ported document is silently inert (measured, ledger 0128).
- **Rendering a restored photograph inside the document.** Section 6.5.

## 4. The manifest

The manifest is a single JSON script block inside the document:

```html
<script type="application/json" id="idea-manifest"> ... </script>
```

Located by BOTH its `type` and its `id`. A document carrying two is REFUSED rather than
resolved by taking the first, because which one `getElementById` returns is not a thing
an author should have to know. The element id is `HTML_MANIFEST_SCRIPT_ID`.

The authority for this section is `src/lib/classroom/html-assignment/manifest.ts`.
Migration 0195's `_classroom_check_html_manifest(jsonb)` is the SQL boundary and restates
everything below that could corrupt a row; the two are asserted against each other.

### 4.1 Shape

```ts
interface HtmlAssignmentManifest {
  schemaVersion: 3;
  kind: 'html-assignment';
  title: string;
  course: string;
  points: number;           // whole, 0..10000
  header?: HtmlBlock[];     // identity fields; no points, never reach the rubric
  modules: HtmlModule[];    // non-empty, at most 40
}

interface HtmlModule {
  id: string;               // HTML_ID_RE, unique across the manifest
  title: string;
  points: number;           // whole, 0..10000
  audience?: 'team' | 'individual';
  blocks: HtmlBlock[];
  criteria: HtmlCriterion[];  // non-empty
}

interface HtmlBlock {
  id: string;               // BECOMES block_id. Permanent.
  field: string;            // the document's own data-field. Renameable.
  type: 'text' | 'longText' | 'checkbox' | 'radio' | 'image' | 'table';
  minSentences?: number;    // whole, 0..100
}

interface HtmlCriterion {
  id: string;               // unique WITHIN its module
  text: string;
  points: number;           // must equal the top level's points
  levels: HtmlLevel[];      // three or four, never two
}

interface HtmlLevel {
  points: number;           // whole, strictly descending, bottom 0, top = maximum
  label: string;
  short: string;            // REQUIRED here. Six words max, no terminal punctuation.
  descriptor: string;
}
```

Caps: `HTML_MAX_MODULES` 40, `HTML_MAX_BLOCKS` 400 (counted across the header and every
module), `HTML_SHORT_MAX_WORDS` 6, criterion level points 0..1000, document bytes
`HTML_DOCUMENT_MAX_BYTES` = 2 MiB.

### 4.2 `id` and `field` are two different strings, and that is load-bearing

**`id` BECOMES `classroom_responses.block_id` AND IS THE JOIN KEY FOR EVERY ANSWER EVER
STORED UNDER IT. It is PERMANENT.** A renamed block id orphans that work SILENTLY: the
row is still there and the answer simply stops rendering. There is no error, no empty
row, and nothing anywhere to say a term of work has been detached.

**`field` is the document author's own name for an input and IS renameable.** It is what
the document writes in its `data-field` attribute, and a later revision may change it
freely.

They are two fields rather than one so that a rename of the document's own vocabulary
cannot reach the join key. In every fixture the two are deliberately different strings,
so a lookup that is the identity function cannot pass for a working mapping.

### 4.3 The id charset is `classroom_responses`'s, not this format's

**`HTML_ID_RE` is `/^[A-Za-z0-9_-]{1,40}$/`**, and it governs module ids, block ids and
criterion ids alike. It is 0086's own rule for authored ids landing in
`classroom_responses.block_id` (whose column CHECK is 1-64 characters), and 0195 restates
the same pattern in SQL. A pattern loosened on one side alone is a row the other refuses,
discovered by a student at the moment they answer.

**THE ORIGINAL CONTRACT NAMED NO CHARSET, AND THAT COST A PORT.** Ledger 0128's port of
`idea100-blade-01` used dotted ids (`identity.mood`, `package.student-name`), 63 of them,
and no surface in the repository would have accepted one. Ledger 0134 converted every dot
to a hyphen, which was safe ONLY because nothing had ever been imported from that fixture
-- that window closes permanently the moment the first real document is imported. Read
the regex in `manifest.ts`; never take it from a prose copy, this one included.

### 4.4 `header` blocks: identity fields with no points

Student name, team, date. They carry no points and never reach the rubric, which is
exactly why they are a top-level array rather than a module.

**WITHOUT IT, AN AUTHOR HAS TO INVENT A 0-POINT MODULE, WHICH RENDERS IN THE GRADING
CONSOLE AS SOMETHING TO SCORE.** That is what ledger 0128 had to do against the original
contract, and it is what `header` exists to prevent.

A header block is a block in every other respect: same id pattern, same uniqueness across
the WHOLE manifest, same field correspondence with the document. A student's name is an
answer, stored under a block id like any other, and losing it to a renamed id loses it
just as silently. A header block declaring `points` is REFUSED by name.

`manifestBlocks()` flattens the header and every module's blocks together, in document
order, and is a function rather than two `flatMap`s at the call sites precisely so a
mapping cannot skip the header and drop every identity field.

### 4.5 A table is ONE block whose value is structured JSON

`type: 'table'` means the block's value is a JSON string of rows, and the document
serialises the WHOLE table whenever any cell changes. **There is no per-cell
`data-field`.**

**THIS IS A CORRECTION, NOT A SIMPLIFICATION.** Ledger 0128's real port carried an
`addMfgRow()` that minted `mfg-06-p` at runtime -- a field no manifest names, which the
parent could only drop silently. That is exactly the orphaning the `id`/`field` split
exists to prevent, arriving through a door the split did not cover: the split protects
against a RENAMED field, and this is an INVENTED one. The undeclared-`[data-field]`
refusal in section 10.2 is what closes it.

### 4.6 `short` is required on every level

The grading console's `levelShort` renders `short` FIRST, ahead of the descriptor. On
2026-09-08 an instructor rewrote descriptors on IDEA209H Unit 1 and saw nothing change on
screen, because nothing in the product could edit `short`. A manifest carries both, every
level, every time, or it is not stored -- refused by the browser validator and by 0195.

It is capped at six words and must not end in `.`, `!` or `?`, per
`IDEA_RUBRIC_STANDARDS`.

### 4.7 Copy rules that are the programme's, not this format's

`validateHtmlManifest` scans every student-facing string -- module titles, criterion text,
level labels, shorts and descriptors, AND the document's own visible prose -- for two
things:

- **A WEEKDAY.** A document naming "Friday" is correct for exactly one section in exactly
  one term; every other class reads a date that is wrong, and the author is never the
  person who finds out.
- **A BRITISH SPELLING**, as one alternation (`BRITISH_SPELLING_RE`).

Each refusal names WHERE it was found, because a document has hundreds of strings and
"British spellings: [licence]" on its own sends an author to read the whole thing.

**THIS IS A DELIBERATE SECOND COPY of a list `tools/validate-assignment-spec.py` already
holds**, because python cannot import TypeScript and the browser cannot run the python
tool. It is a MIRROR in the sense `docText` mirrors `_classroom_doc_text`, and what keeps
the two honest is not discipline: `tests/html-assignment-manifest-parity.test.ts` reads
the python source and asserts both lists match term for term.

**0195 DOES NOT CHECK THE COPY RULES OR THE FIELD CORRESPONDENCE, and that boundary is
deliberate.** Every one of them requires reading the HTML, and a second HTML scanner
written in plpgsql is a parser that drifts from the one the importer actually runs --
which is worse than the gap, because a document would then pass one and fail the other
with nothing able to say which was right. What 0195 refuses is everything that would
corrupt a ROW: ids, uniqueness, the level rules and the arithmetic.

## 5. The security boundary

**SCRIPTS WITHOUT `allow-same-origin` IS THE WHOLE MODEL.** Everything else in this
section is defence in depth around that one absence.

The flag set is `HX_SANDBOX_FLAGS`:

```
allow-scripts allow-popups allow-popups-to-escape-sandbox
```

An `<iframe>` sandboxed without `allow-same-origin` puts the document in a unique OPAQUE
ORIGIN. It has no parent DOM, no cookies, no credentialed fetch, and none of
`ideabosco.com`'s `localStorage`. It therefore cannot write to the database and cannot
learn anything about the session. Everything it wants to record it says in a
`postMessage`, and the PARENT decides what -- if anything -- that means.

**THE TWO POPUP FLAGS ARE A DELIBERATE WIDENING, AND SECTION 5.6 STATES WHAT THEY COST.**
They do not touch the absence above; they let the document open a link in a new tab, which
without them it cannot do at all.

**TWO FLAGS ARE REFUSED IN EVERY CONFIGURATION**, because neither is about what a document
may do to ITSELF: `allow-top-navigation` (a redirect out of the worksheet, in the tab the
student is working in) and `allow-forms` (a form inside the document submitting somewhere,
which `form-action 'none'` refuses a second way).

**THE PAIR CANCELS THE SANDBOX OUTRIGHT.** A document that is same-origin with its parent
can reach `parent.document`, strip the `sandbox` attribute off its own `<iframe>` element
and reload with full rights. Measured in the container's Chromium against the real route
(ledger 0126, re-run in full by ledger 0153): under this set, `parent.document`,
`document.cookie` and `localStorage` each throw `SecurityError`; add `allow-same-origin`
and all three succeed, with `localStorage` handing back a value the PARENT wrote.

**`HX_SANDBOX_FLAGS` in `bridge.ts` IS THE ONE SPELLING.** `HtmlAssignmentFrame.svelte`
writes it into the element and `hxDocumentCsp` writes it into the header. A second literal
is a framed document and a navigated one drifting apart with nothing able to compare them.

### 5.1 Why a second origin, and not a header on the main host

A header governs scripting and document origin; **it does not govern whether a SUBRESOURCE
request carries credentials.** A document containing `<img src="/api/whatever">` served
from `ideabosco.com` reaches the real backend with the viewer's cookies attached. Served
from a different site it reaches a host that holds no session.

**THE ABSENCE IS STRUCTURAL, NOT BEHAVIOURAL.** `@supabase/ssr` sets the session cookies
with no `Domain` and with `httpOnly: false`, so they are host-only on `ideabosco.com` and
readable by `document.cookie`. The host a student's uploaded document runs on is exactly
the question, and an absence cannot regress.

`PUBLIC_HX_SANDBOX_ORIGIN` names that host. **Unset means the route answers on ANY host**,
which is what makes local development and every Vercel preview work with no configuration
at all. `hxOnServingHost` is one handler declining an origin it is not for, inside its own
body -- it is NOT the `hooks.server.ts` host branch that cost Foundry two lanes.

### 5.2 The CSP, directive by directive

`hxDocumentCsp(portalOrigin)` in `src/routes/hx/_headers.ts`:

```
sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox;
default-src 'none';
script-src 'unsafe-inline';
style-src 'unsafe-inline';
img-src data: blob:;
connect-src 'none';
form-action 'none';
frame-ancestors <portal origin>
```

- **`sandbox`** -- sections 5.3 (why the directive exists) and 5.6 (the popup flags).
  **A popup is a NEW browsing context with its own policy**, so nothing else in this list
  is weakened by them: `connect-src`, `form-action` and `frame-ancestors` still govern
  THIS document exactly as they did.
- **`script-src` / `style-src` `'unsafe-inline'`** -- a ported document is one file with
  its script and its style inline. **No host is admitted on either**, deliberately: there
  is no CDN reach here, and that is the difference between this and a Foundry bundle.
- **`img-src data: blob:`** -- a pasted photograph, as bytes the document already holds.
  No remote image, so no document can phone home by setting an `<img src>`, which is the
  exfiltration channel a `connect-src` alone leaves open.
- **`connect-src 'none'`** -- THE ONE THAT STOPS AN UPLOADED DOCUMENT EXFILTRATING STUDENT
  ANSWERS. `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` and `sendBeacon` all
  refused. **It is an INDEPENDENT lever from the sandbox and neither is evidence about the
  other:** measured, a fetch from inside the frame is refused with this directive in force
  whether or not `allow-same-origin` is granted. The discriminator, also measured: open
  `connect-src` with the sandbox intact and a credentialed fetch still refuses; drop both
  and it answers 200.
- **`form-action 'none'`** -- the same exfiltration answered a second way.
- **`frame-ancestors`** -- section 5.4.

Alongside the policy, every served document carries `x-content-type-options: nosniff`,
`referrer-policy: no-referrer`, `cache-control: private, max-age=60` (the bytes are
immutable, but WHO may read them is not) and `x-robots-tag: noindex, nofollow`.

### 5.3 CORRECTION: the CSP needs a `sandbox` directive, and the original had none

**Measured by ledger 0126, closed by ledger 0134.**

The iframe `sandbox` ATTRIBUTE is on the `<iframe>`, so it governs a document the PORTAL
FRAMED and nothing else. A student who navigates STRAIGHT to `/hx/<docId>` -- typed,
pasted, or followed from a link -- reaches the same bytes with no frame around them and
therefore no attribute, so the document is **NOT placed in an opaque origin**.

With `PUBLIC_HX_SANDBOX_ORIGIN` unset, which is production's configuration today,
`hxOnServingHost` answers true for every host and the route answers on `ideabosco.com` --
the host the portal's session cookies live on, and the host they are written `httpOnly:
false` so `document.cookie` can read them. An uploaded document navigated to directly
would run in that origin, with that session.

The CSP `sandbox` directive covers the document however it was reached. **0134 proved it
by DIRECT NAVIGATION in the container's real Chromium, with a cookie planted on the
serving origin as a positive control**, across a five-case matrix: baseline `window.origin`
is `"null"`, `document.cookie` and `localStorage` throw `SecurityError`, and a credentialed
`fetch` throws `TypeError`; remove the directive and all three reach, reading the planted
token back; open `connect-src` with the sandbox intact and the fetch still refuses; drop
both and it answers 200.

**RE-RUN IN FULL BY LEDGER 0153 AGAINST THE WIDENED FLAG SET, because the widening changes
the thing 0134 proved.** Same instrument, same planted cookie
(`hx_proof_sentinel=PARENT-SECRET-0153` on the serving origin, read back from an ordinary
page on that origin first, so the control is known live). Both halves, because the two
mechanisms are different and each is meaningless where the other applies:

| probe | (A) direct navigation | (B) framed |
| --- | --- | --- |
| `window.origin` | `"null"` | `"null"` |
| `document.cookie` | REFUSED `SecurityError` | REFUSED `SecurityError` |
| `localStorage` | REFUSED `SecurityError` | REFUSED `SecurityError` |
| `window.parent.document` | n/a, parent is self | REFUSED `SecurityError` |
| `window.top.location` | n/a, top is self | REFUSED `SecurityError` |
| credentialed `fetch` | REFUSED `TypeError` | REFUSED `TypeError` |

0 of 5 reached in either half, and `location.href` was asserted unchanged afterwards so
the refusals are the document's and not an error page's.

**ONE INSTRUMENT NOTE, BECAUSE IT COST A WRONG READING FIRST TIME.** The direct-navigation
half must NOT use the hostile `/hx/probe` fixture. On a direct hit `window.top` IS the
document's own window, so the probe's `window.top.location = 'https://example.com/'` line
NAVIGATES THE PAGE AWAY, and every reading taken afterwards is taken on a
`chrome-error://chromewebdata/` page -- which reports `document.cookie` as refused for
entirely the wrong reason and reports `parent.document` as REACHED. Use an ordinary
document and assert `location.href`.

**`PUBLIC_HX_SANDBOX_ORIGIN` IS DEFENCE IN DEPTH NOW, NOT A PREREQUISITE**, and remains
the stronger deployment: a second host's cookies are not merely unreadable, they are not
there.

**FOUNDRY'S CONDITIONAL `allow-same-origin` GRANT DOES NOT TRANSFER HERE.** Foundry grants
the flag when the bundle origin and the portal origin differ, which its own host gate
guarantees. This route has no such guarantee -- with the sandbox origin unset it answers
on the portal host itself -- so withholding it unconditionally is the only correct answer
and the condition Foundry can assert is one this route cannot.

### 5.4 `frame-ancestors` is resolved, not written out

`hxPortalOrigin(configured, sandboxOrigin, requestOrigin)`, a three-rung ladder mirroring
Foundry's `foundryPortalOrigin`:

1. `PUBLIC_HX_PORTAL_ORIGIN` when it is set. An operator who names an origin means it.
2. Otherwise `HX_PORTAL_ORIGIN` (`https://ideabosco.com`, the contract's own literal) --
   **but only when `PUBLIC_HX_SANDBOX_ORIGIN` is itself set.**
3. Otherwise the origin the request arrived on.

**WHY THE SANDBOX ORIGIN GATES RUNG 2.** A configured sandbox origin is what makes this a
split-origin deployment, so the portal is by construction a different host and naming it
is the only answer that works: that is production, and rung 2 reproduces the contract's
policy byte for byte with nothing configured. With the sandbox origin unset the route
answers on any host -- dev and preview, where one server answers both roles -- and rung 2
would name a host that is not doing the framing, blanking every frame. Rung 3 names the
server that served the document, which on a one-host deployment IS the portal, and can
never widen production because production never reaches it.

**ON A PREVIEW, LEAVE BOTH UNSET.** Naming one origin there makes `frame-ancestors` name
a host that is not doing the framing, and the browser refuses to embed the document at
all, which reads as a broken feature.

`hxPortalOriginIsRequestHost` reports whether rung 3 produced the answer, and is read by
the dev harness: "`frame-ancestors` is the production portal" and "`frame-ancestors` is
whatever host you happen to be on" are different facts about a deployment.

### 5.5 Every refusal is the same bodyless 404

A malformed handle, an unknown document, an unpublished or scheduled-ahead item, an item
that is not an assignment, a dev fixture asked for in production, a deployment with no
service key, a `/hx/` path on the wrong host, and a method that is not GET or HEAD are
all indistinguishable from outside. `no-store`, so a 404 for a document about to be
published is not cached into the next viewer's browser.

**THE PUBLICATION GATE IS NOT A SESSION CHECK, AND THAT IS FORCED RATHER THAN CHOSEN.**
There IS no session on the sandbox origin -- that absence is the point of the split -- so
requiring a signed-in caller means either `Domain`-scoping the portal's cookies onto that
host, or putting a signed token on every request, which is the machinery Foundry spent
five lanes removing. The licence comes from the ITEM'S OWN publication state.

**WHAT THAT COSTS, STATED RATHER THAN DISCOVERED: a teacher cannot preview an UNPUBLISHED
item's document.** The frame renders empty and reads as a broken upload. The answer when
that has to close is a second read on the PORTAL origin that gates on who is asking, not
a looser gate here -- a flag on `hxStoredDocument` would put one boolean between every
unpublished document and the open internet.

### 5.6 The popup flags: what they buy, what they cost, and what was measured

**DECIDED BY MR. PINA ON 2026-09-11, SHIPPED BY LEDGER 0153.** The set gained
`allow-popups allow-popups-to-escape-sandbox`. This is a WIDENING of the boundary the rest
of this section describes, and it is recorded as one rather than as housekeeping.

**WHAT IT BUYS.** Without the flags a ported document cannot open a link in a new tab at
all: `window.open` returns `null` and a `target="_blank"` anchor does nothing. IDEA100
Blade CAD 01 ships an Open slides button, which is inert without them and works the moment
they land.

**BOTH FLAGS ARE REQUIRED, AND THE SECOND IS NOT POLISH. MEASURED, NOT ASSUMED.** A popup
opened under `allow-popups` alone INHERITS this sandbox:

| flags on the frame | `window.open` returns | popup `window.origin` | popup `document.cookie` | popup `localStorage` |
| --- | --- | --- | --- | --- |
| `allow-scripts` (pre-0153) | `null` -- blocked | no popup | no popup | no popup |
| `+ allow-popups` | a `Window` | `"null"` (opaque) | REFUSED `SecurityError` | REFUSED `SecurityError` |
| `+ allow-popups-to-escape-sandbox` | a `Window` | the URL's real origin | the popup origin's own | the popup origin's own |

Google Slides cannot run in an opaque origin with no storage, so `allow-popups` alone
would leave the Open slides button opening a blank tab -- which reads as a broken link
rather than as a policy. **A later edit that trims the second flag as redundant reverts the
feature to that.**

**WHAT THE POPUP CAN ACTUALLY DO.** Measured in the container's Chromium (141.0.7390.37)
by ledger 0153, from a REAL TRUSTED CLICK inside the framed document -- a
`page.evaluate(() => window.open())` is refused by the popup blocker for lack of a user
gesture and would read as the sandbox refusing it. The popup was opened at an origin
GENUINELY FOREIGN to the portal, which is what a hostile document would do
(`localhost:5199` and `127.0.0.1:5199` are the same server at different origins, which is
the shape needed without leaving the container):

| from the popup | result |
| --- | --- |
| `window.origin` | its own real origin -- a normal browsing context, not opaque |
| `window.opener` | present, a cross-origin `Window` proxy to the sandboxed frame |
| `opener.document` | REFUSED `SecurityError` |
| `opener.parent.document` | REFUSED `SecurityError` |
| `opener.top.document` | REFUSED `SecurityError` |
| `opener.location` read / write | REFUSED `SecurityError` |
| `opener.top.location` read / write | REFUSED `SecurityError` |
| `opener.postMessage` | does not throw; the bridge drops it (`hxReceive` requires `event.source` to be the frame's own `contentWindow`) |

**And confirmed from OUTSIDE the popup rather than on its own say-so:** after both write
attempts the parent tab was still at its own URL and the document frame was still at
`/hx/worksheet`. **So the widening did NOT buy top navigation by proxy** -- the flag the
frame is denied is not reachable through a window it opens.

**WHAT THE DOCUMENT CAN DO TO ITS OWN POPUP**, the other direction: `popup.document`,
`popup.location` (read) and `popup.origin` are all REFUSED `SecurityError` -- the frame is
opaque, the popup is not, so they are cross-origin. It CAN navigate the popup
(`popup.location.href = ...` took effect, measured from outside) and `postMessage` to it.
Neither adds anything: it could have opened that URL directly.

**A POPUP AT THE PORTAL'S OWN ORIGIN IS AN ORDINARY PORTAL PAGE, AND THAT IS NOT A
CAPABILITY THE DOCUMENT GAINS.** Opened at the portal's own origin (measured against the
dev portal origin, not against production), the popup is same-origin with the portal tab
and can walk `opener.parent` into it -- measured, it read the parent page's title. That is
OUR page reading OUR page. The document cannot script it (every read above is refused
across the opaque boundary) and cannot inject anything into it.

**WHAT IT COSTS, STATED PLAINLY RATHER THAN REASSURINGLY.** An uploaded document can now
open a normal, unsandboxed tab at any URL it chooses. **That is a stronger phishing surface
than the same fake form drawn inline in the worksheet**, because the new tab carries a real
address bar and a real lock icon, which a reader has been taught to believe. A document
that draws a Google sign-in box inside the frame is obviously inside a worksheet; one that
opens a convincing page in its own tab is not.

**THE MITIGATION ON RECORD IS THAT IMPORT IS ADMIN-ONLY**, a first-season decision. There
is no content scan, no URL allowlist and no interstitial: the person who uploads a document
is trusted, and that trust is the whole of the control. If documents are ever accepted from
a wider set of authors than admins, **this is the decision that has to be revisited first**,
and the narrower answer is to drop `allow-popups-to-escape-sandbox` (accepting that slide
links stop working) rather than to add a scanner.

## 6. The bridge protocol

The authority is `src/lib/classroom/html-assignment/bridge.ts`. Every rule about whether a
message counts lives there as a PURE FUNCTION with no DOM in it, so it can be put to a
hostile input without a browser. `HtmlAssignmentFrame.svelte` owns the element and the
listener and owns no rules.

### 6.1 Messages

Frame to parent (`HxFrameMessage`):

| Type | Payload |
|---|---|
| `idea:ready` | `schemaVersion: number` |
| `idea:change` | `field: string`, `value: string \| boolean` |
| `idea:image` | `field: string`, `name: string`, `bytes: string` (base64) |
| `idea:image-remove` | `field: string` |
| `idea:image-caption` | `field: string`, `caption: string` |
| `idea:height` | `px: number` |

Parent to frame (`HxParentMessage`):

| Type | Payload |
|---|---|
| `idea:state` | `values: Record<field, string \| boolean>`, `images: Record<field, HxImageState>`, `readOnly: boolean` |
| `idea:saved` | `at: string`, `ok: boolean`, `schemaVersion: 3`, `reason?: string` (only when `ok` is false) |

Both outbound messages are built by `hxStateMessage` and `hxSavedMessage` so the component
cannot invent a third.

`images` on `idea:state` is REQUIRED rather than optional. An optional field is one a
caller forgets, and forgetting it means a student reloads a worksheet and their
photographs are gone from it -- which looks exactly like the upload never worked. An empty
object costs one pair of braces.

`reason` on `idea:saved` is present ONLY on a failure -- absence is the mechanism, and a
`reason` beside `ok: true` would be a document rendering an explanation for something that
worked. A failure with no reason falls back to one sentence, because "not saved" alone is
the message this repository already refuses to ship on its own surfaces.

**THE SCHEMA VERSION RIDES THE ACKNOWLEDGEMENT, NOT ONLY THE HANDSHAKE**, so a document
served from a stale cache learns it is talking to a parent on a different contract at the
first write rather than never.

### 6.2 CORRECTION: `event.origin` from a sandboxed frame is the string `"null"`

**Measured by ledger 0126. This is the correction that would otherwise make the whole
feature silently inert.**

The original contract said the parent "validates `event.origin` against the document
origin on every message and drops anything else". Implemented as a literal comparison
against `https://sandbox.ideabosco.com`, **that rule DROPS EVERY REAL MESSAGE**: the
sandbox the contract itself mandates is exactly what makes the document's origin OPAQUE,
and `postMessage` serialises an opaque origin to the string `"null"`. There is no error
anywhere. Nothing throws, nothing logs, and the feature is simply dead.

Measured in the container's Chromium against the real route: with
`sandbox="allow-scripts"` every message arrives with `event.origin === "null"` and
`window.origin` inside the frame reads `null`; add `allow-same-origin` and the same message
arrives carrying the real origin.

**SO THE EXPECTED ORIGIN IS DERIVED FROM THE SANDBOX FLAGS RATHER THAN WRITTEN DOWN:**

```ts
hxExpectedOrigin(documentOrigin, sandboxFlags)
  // 'null' unless the flags grant allow-same-origin,
  // in which case normalizeOrigin(documentOrigin)
```

That keeps the rule honest in both directions. It is still a real check against a real
expectation, it cannot be read as "we ignore the origin", and if anybody ever weakens the
sandbox this function starts demanding the concrete origin in the same breath -- the two
cannot drift.

**`"null"` IS NOT BY ITSELF AN IDENTITY, WHICH IS WHY THE SOURCE CHECK IS LOAD-BEARING.**
Every opaque-origin document in the world serialises to the same string, so the origin
check alone narrows a message to "came from something sandboxed" and no further.

### 6.3 CORRECTION: the CSP refuses all three IDEA typefaces

**Measured by ledger 0128** (the port-fixture lane) -- see section 12 for the attribution
correction this document also carries.

A ported document that opens with

```css
@import url('https://fonts.googleapis.com/css2?family=Orbitron...&family=Share+Tech+Mono&family=Rajdhani...');
```

loses **all three typefaces and therefore its entire visual identity**. `style-src` is
`'unsafe-inline'` with no host, so the `@import` is refused by name; and **there is no
`font-src` at all**, so the font files would fall to `default-src 'none'` even if the
sheet loaded. Both halves have to be fixed; fixing either alone changes nothing.

**IT WAS MEASURED BY RENDERED WIDTH, BECAUSE `document.fonts.check()` IS VACUOUS HERE.**
Against an unknown-family baseline of 714.56px, Rajdhani, Orbitron and Share Tech Mono
each measure 714.56px, while an installed family (monospace) measures 838.06px -- so the
instrument can tell a loaded family apart, and none of the three is loaded.
`document.fonts.check('48px Rajdhani')` claims **true** with **0** `@font-face` rules in
the document: with the stylesheet refused there is no rule to be pending, so `check()`
answers true for a font that does not exist. **Never assert a font claim with
`document.fonts.check()` on this surface.**

**THIS IS UNFIXED ON THE TREE AS OF 2026-09-10.** The CSP still carries no `font-src` and
no host on `style-src`.

**THE SHAPE OF THE FIX IS FOUNDRY'S `/_platform/fonts.css`, WHICH IS ALREADY SOLVED ONE
SUBSYSTEM OVER.** Serve the faces from an origin the policy names, with
`access-control-allow-origin: *` -- load-bearing rather than decorative, because an opaque
origin makes even a same-host font fetch cross-origin, and a `@font-face` request is
CORS-mode by specification. Admitting `fonts.googleapis.com` and `fonts.gstatic.com`
instead is the wrong answer for the same reason `connect-src 'none'` is right: it puts a
remote host back on a document whose whole containment argument is that it reaches
nothing.

### 6.4 What `hxReceive` refuses, in order

**THE ORDER IS THE SECURITY MODEL AND IT IS NOT ARBITRARY.** Provenance first, because a
message from somewhere else must be dropped before anything reads a byte of its payload.

1. **ORIGIN.** `incoming.origin !== hxExpectedOrigin(...)`. Section 6.2.
2. **SOURCE.** `event.source` must be the frame's own `contentWindow`. A null
   `frameWindow` is the pre-mount state and refuses everything -- fail-closed, rather than
   treating "we do not know" as a pass. **THIS IS THE CHECK THAT BITES IN DEVELOPMENT:**
   locally and on a preview one server answers both roles, so "is this from the document
   origin" cannot separate the frame from the page around it. A `Window` reference cannot
   be forged. In production the origin check adds the second, independent refusal.
3. **SHAPE.** A plain object with a known string `type`, and every field that type
   requires at the type it requires.
4. **SCHEMA.** `idea:ready` announcing anything but 3 is reported, not tolerated.
5. **FIELD.** Resolved to a `block_id` through the parent's own map (section 6.6).

Plus two ceilings, each a REFUSAL and never a clamp or a truncation:

- **`HX_MAX_HEIGHT_PX` = 40,000.** `idea:height` is the one number the frame controls that
  the PARENT applies to its own layout, so it is the one place a hostile or merely buggy
  document can reach out of its box: an `<iframe>` at 100,000,000px is a page nobody can
  scroll, on a surface with a Submit control on it. 40,000px is far past any real worksheet
  (the longest ported document measured under 9,000px) and far short of breaking the page.
  Clamping would silently show a document a size it did not ask for and give nobody a
  reason to look.
- **`HX_MAX_CAPTION_CHARS` = 500.** Silently storing half of what somebody typed is the
  worse outcome of the two.

**A DROP IS REPORTED, NEVER SILENT.** Every refusal comes back as
`{ ok: false, reason, detail }` with `reason` drawn from a closed union (`origin`,
`source`, `shape`, `type`, `schema`, `field`, `value`, `caption`, `height`). These are
DISTINCT on purpose: "a message from somewhere else" and "a field this document does not
declare" are different events, and a surface counting them wants to tell them apart.
Silence would make a renamed field indistinguishable from a working one.

### 6.5 Images: bytes go frame-to-parent only, never back

`idea:image` carries a base64 payload UP. What returns in `idea:state` is an
`HxImageState` -- a URL the parent minted by putting those bytes through the ORDINARY
submission-file path (`uploadClassroomFile`'s `role: 'submission'`), plus the document's
own `name` for display and the student's `caption`.

Three reasons, and the third is the one that would not be obvious:

1. A reload would otherwise have to re-send every photograph a student ever attached,
   through `postMessage`, on a phone. The state message for a six-module worksheet with
   three pictures in it is megabytes.
2. The stored artefact is a `classroom_submission_files` row like every other hand-in, so
   it is one thing to grade, one thing to export and one thing to delete.
3. **`img-src data: blob:` WOULD HAPPILY RENDER A ROUND-TRIPPED DATA URI** -- which is
   exactly why this is written down rather than left to fail loudly. It would work, and it
   would quietly make the document the system of record for a student's photograph.

**CORRECTION (ledger 0128): the original contract's `idea:image` was ADD-ONLY and
`idea:state` could not carry an image back.** The contract carried `{field, name, bytes}`
and nothing else: no message that unsends an image, no field for a caption, and no id by
which parent and frame could agree which image is which. `values` was
`Record<string, string | boolean>` and an image is neither. **So a student reopening the
worksheet got their text and an empty sketch list, and module 04 of the Blade port is 10
of 50 points.** The current protocol closes it with `images` on `idea:state` and two
further frame-to-parent messages:

- **`idea:image-remove` IS ITS OWN MESSAGE, NOT AN `idea:image` WITH EMPTY BYTES.** An
  empty byte string is a legitimate-looking payload that would have to be special-cased in
  the upload path -- which is where a zero-byte file would then be created and immediately
  deleted -- and it gives a document two spellings for one intent.
- **`idea:image-caption` IS SEPARATE FROM THE BYTES BECAUSE IT IS A SEPARATE EDIT.** A
  student retypes a caption far more often than they replace the photograph; folding the
  two together means re-sending the image on every keystroke of the caption.

**A RESTORED PICTURE STILL CANNOT RENDER INSIDE THE DOCUMENT.** `HxImageState.url` is a
same-origin portal proxy URL, the served CSP is `img-src data: blob:` with no host on it,
and the request would arrive credential-free at a route that needs a session even if the
policy admitted it. **The repair that needs no weakening of the CSP is to render a restored
picture in PARENT CHROME beside the frame, where Submit already lives.** Widening `img-src`
is the one that does not work anyway.

### 6.6 A frame naming a `block_id` gets nowhere, and the mechanism is absence

`idea:change` names a `field`, never a `block_id`. The parent looks that field up in
`fieldToBlockId` -- a map it built from the manifest it stored AT IMPORT -- and a field
that is not in there is DROPPED rather than guessed at.

**There is no branch in `hxReceive` that reads a `block_id`, a `blockId`, a `block`, or
anything else off the incoming payload.** So a document sending
`{ type: 'idea:change', block_id: 'x', value }` is dropped for having no `field` at all,
and one sending a `field` whose value happens to BE a block id is dropped unless that same
string is also a declared field name. Nothing needs to recognise the attack; there is
simply nothing for it to reach.

`resolveField` uses `Object.hasOwn` rather than a bare lookup. Without it, a document
sending `field: "constructor"` or `field: "toString"` resolves through the prototype chain
to a FUNCTION, which is truthy, and the caller then holds a "block id" that is a chunk of
JavaScript source.

`htmlFieldToBlockId` in `mount.ts` is the page-payload caller. Its precondition guard asks
only what the walk needs -- arrays where arrays go, blocks with a string `id` and a string
`field` -- and **an empty record FAILS CLOSED**: the bridge drops every message naming a
field it does not hold, so a manifest that cannot be walked yields a worksheet that saves
nothing rather than one that writes to a guessed block id.

### 6.7 `hxPostTarget` is `'*'`, which looks wrong and is not

`postMessage`'s `targetOrigin` is a REFUSAL: the browser delivers only if the receiving
document's origin matches. **The receiving document is in an opaque origin, and an opaque
origin matches no origin string that can be written down** -- so any concrete target
silently drops every message the parent sends.

What `'*'` normally risks is that the frame might have navigated somewhere else. What we
send is a student's own answers back to them and a save acknowledgement: no token, no
session, no identity, nothing the document did not already give us -- and the frame can
only navigate within a sandbox that grants no top-level navigation.

## 7. What the sandbox costs

Stated together so nobody discovers one of these during a port.

- **`localStorage` THROWS.** Not "returns null" -- the GETTER throws in an opaque origin,
  so the first line of a document that reads saved state takes the page down before
  anything renders. **A ported document's autosave must be deleted and replaced by the
  bridge.** (Foundry solves the same problem with an injected shim; that is not available
  here, because injecting anything into a document would end the byte rule that lets a
  reviewer read what executes.)
- **DOWNLOADS DO NOT FIRE** without `allow-downloads`, which is not granted. A "Download
  with Data" control in a ported document is inert.
- **`window.print()` IS DEAD AND SAYS NOTHING.** Chromium logs `Ignored call to 'print()'.
  The document is sandboxed, and the 'allow-modals' keyword is not set.` and `print()`
  returns without throwing. A Print / Export PDF control is silently inert.
- **THE DOCUMENT CANNOT UPLOAD A FILE ITSELF.** Image bytes come up as `idea:image` and
  the PARENT uploads them.
- **NO NETWORK OF ANY KIND.** `connect-src 'none'`, no host on any fetching directive.
- **NO FONTS.** Section 6.3.
- **NO TOP-LEVEL NAVIGATION**, and no popups escaping the sandbox.
- **SUBMIT IS NOT THE DOCUMENT'S.** A Submit inside the document would be a button whose
  handler the document itself wrote. It is a parent control in parent chrome, and so is
  the completeness check (`hxIncompleteBlocks`, counting sentences in the STORED values
  against each block's `minSentences` from the manifest the parent stored at import).

`item_id` is the primary key of `classroom_html_assignments`, exactly as it is for

**THE HANDLE IS NOT THE ITEM ID, AND THAT IS ONE COLUMN BUYING A REAL THING.** The serving
origin holds no session, so whatever appears in that URL is readable by anyone who has it.
An item id appears in the signed-in classroom URL a teacher projects on a whiteboard, so
reusing it as the public handle would make a glance at that URL enough to pull the raw
document off a host with no session.

**ZERO CLIENT WRITE GRANTS.** The one write is
`classroom_set_html_assignment(p_item_id, p_document, p_manifest, p_filename)`, SECURITY
DEFINER, with two gates in this order:

1. **`_classroom_manages_item` -- the PERMANENT bar**, the same one editing the item
   carries, because a ported document changes what every posted class's students are asked
   to do.
2. **`is_admin()` -- the SEASON bar.** Upload is admin-only for the first season. It is
   written as its own statement, named as the season gate, so lifting it is deleting one
   `if`. Were it the only gate, deleting it would open the write to every signed-in
   account, which is why the permanent bar goes first and stands on its own.

A null document REMOVES, and removing is recoverable: the displaced document is
snapshotted first, exactly as 0110 made "Remove" recoverable for a spec.

**`/hx` IS A RESERVED SLUG IN BOTH HALVES AT ONCE** -- `RESERVED_SLUGS` in
`src/lib/short-links.ts` and `_app_short_link_reserved` (migration 0196) -- because it is a
top-level slug-shaped route that SvelteKit resolves ahead of the `[shortlink]` catch-all.

**THE SERVING READ IS SERVICE-ROLE AND IS NOT THE LAST WORD ON ACCESS.**
`$lib/server/html-assignment-document.ts` is the ONE reader of
`SUPABASE_SERVICE_ROLE_KEY` for this subsystem (a FIFTH reader repo-wide; `CLAUDE.md`'s
"exactly FOUR places" sentence is stale and is reported rather than edited here). It
re-checks, on every request, what RLS would have enforced: the handle is a uuid, the row
exists, the item is an assignment, and the item is published and not scheduled ahead --
`_classroom_item_live`'s own condition, expressed as `published && !isScheduled(item)`
rather than re-typed.

## 9. The write gate: no answer can currently be stored

**AS OF THE TREE READ FOR THIS DOCUMENT -- `origin/integration` at `b2581959`, 2026-09-10
-- MIGRATION 0197 IS NOT PRESENT. The highest migration in `supabase/migrations/` is
0196.** A lane (ledger 0138) is understood to be fixing this concurrently; when 0197
lands, this section is what it supersedes, and the paragraph below describes the state it
found.

`classroom_save_response` (defined in 0086, last replaced in 0128) is **the only function
in the schema that writes `classroom_responses`**, and a ported assignment cannot use it.
Three independent refusals, each measured against a real embedded Postgres with the real
migration chain applied (`tests/db/html-assignment-write-gate.test.ts`,
`tests/db/html-assignment-round-trip.test.ts`):

1. **IT REQUIRES A SPEC ROW.** Its first statement reads `classroom_assignment_specs` for
   the item and raises `This assignment has no interactive spec.` when there is none. A
   ported assignment carries a MANIFEST in `classroom_html_assignments` and no spec.
2. **IT RESOLVES THE BLOCK ID INSIDE THAT SPEC.** `jsonb_array_elements(v_spec->'modules')`
   down to `b.blk->>'id' = p_block_id`, raising `Unknown block "%".` otherwise. Manifest
   block ids are unknown to it.
3. **ITS TYPE GATE SPEAKS THE WRONG VOCABULARY.**
   `if v_type not in ('textField', 'table', 'checklist')`, against manifest types
   `text`, `longText`, `checkbox`, `radio`, `image`, `table` -- **an overlap of ONE.**

**SO GIVING THE ITEM A COMPANION SPEC IS NOT A REPAIR EITHER**, and that is the important
half: even with a spec row present and the block ids duplicated into it, five of the six
manifest block types would still be refused by the type gate.

`classroom_add_submission_file` carries the identical gate on its `p_block_id` path, so a
block-bound image cannot land either.

**THE SHAPE OF THE REPAIR IS ONE BRANCH IN 0086'S OWN FUNCTION** -- resolve the block
against the manifest when the item carries an HTML assignment, exactly as it resolves it
against the spec otherwise. **DO NOT ANSWER IT WITH A SECOND WRITE PATH.** A private RPC
for HTML answers is a second definition of what an answer is, and 0195's own header gives
the reason that would be wrong: the feature is additive precisely because nothing about an
answer moves.

### 9.1 The feature is inert on purpose, and inertness is structural

No route supplies `htmlAssignmentTransports` and none calls
`createHtmlAnswerTransports`, which exists in `transports.ts` with no caller. Therefore:

- **Nothing can create a schema-3 item.** The composer's import panel is removed by the
  absent transport.
- **A schema-3 item renders READ-ONLY.** `htmlAssignment` IS handed down by the item
  page's load, so the real document renders through the real frame -- but no `htmlAnswers`
  controller is passed, so `ItemDetail` hands the frame no write callbacks and tells it
  `readOnly: true`.
- **`/hx/` serves a table with no rows** in production, plus two dev-only fixtures.

**A WORKSHEET THAT TAKES TYPING AND SAVES NOTHING IS THE ONE FAILURE WORTH AVOIDING HERE.**
That is why read-only is structural -- no answers controller means no callback is handed
down, so there is no write to execute rather than a write that is merely hidden -- and not
a flag a component has to remember to read.

`tests/db/html-assignment-write-gate.test.ts` is the standing measurement. **Delete it
rather than invert it** if the gate is ever widened.

### 9.2 Two smaller measured gaps in the answer path

Reported by ledger 0134 and unclosed on this tree:

- **`createEngineTransports.saveResponse` DROPS THE SQLSTATE.** It funnels every error
  through the file's shared `fail()` helper, which keeps `message` and nothing else, so a
  deadlock and a considered refusal arrive at `HxAnswers` identical. It follows
  `$lib/pg-errors`' own rule for that case -- an ABSENT code is not a transient, so an
  unclassified failure is reported once rather than retried five times. The one-line
  repair belongs in `fail()`, shared by ~50 call sites.
- **`HX_REFUSALS.locked` IS WORD FOR WORD `AssignmentEngine.svelte`'s OWN SENTENCE**, so a
  student who works in both kinds of assignment reads one sentence rather than two. That
  component holds the twin as a PRIVATE function (`refusalText`) and cannot be imported
  today; it is a MIGRATION CANDIDATE for the bundle that owns that file, not a second
  sanctioned copy.

## 10. Validation at import

**THE VALIDATOR REFUSES; IT NEVER REPAIRS.** No coercion, no default filled in, no "close
enough". A document that fails comes back with **every** problem named, and nothing is
stored. Half a manifest is worse than none.

**EVERY PROBLEM IS COLLECTED, never just the first.** An author fixing one refusal at a
time through six round trips of a whole document upload is how a format gets abandoned.
The one exception is a shape so broken that continuing would produce noise -- no manifest,
unparseable JSON, no modules array -- where the later checks would report the absence of
things nobody wrote.

**THE WHOLE DOCUMENT IS VALIDATED AT STAGE TIME, NOT AT SAVE TIME.** A ported document IS
the entire assignment, so a refusal after Post is a refusal after the only work anybody
did. Validation is pure and local, so there is no reason to defer it.

**A FAILED WRITE KEEPS WHAT DID NOT LAND.** The item is created first, the document is
attempted, and only a document that actually landed is cleared. Saving again retries
exactly the rest rather than asking a teacher to find the same file twice.

### 10.1 The file-shaped refusals

`stagedHtmlIssue(file)` checks **type AND size**, and the message states the LIMIT as well
as the value. It reads the FILENAME as well as `File.type`, because `File.type` is
legitimately empty for a file dragged out of some archivers and an empty type must not
read as "not HTML"; a type that is PRESENT and is not `text/html` is refused whatever the
extension says, because that is a `.html` somebody renamed.

The 2 MiB cap is the DATABASE's, not the platform's -- the bytes go through an RPC as
jsonb, so the binding limit is `pg_column_size` and 0195 refuses the same number in the
same words. A client cap looser than the server's is a refusal a teacher only meets after
waiting for the upload.

### 10.2 The document/manifest correspondence, BOTH directions

`documentFields(html)` collects every `data-field` the document declares on a real
element. **Comments, `<script>` and `<style>` regions come out first, on every scan**: a
`data-field` inside a comment is not an input, and one written as a string inside the
document's own JavaScript is the shape a ported document routinely carries (its autosave
enumerates them). Counting either as a real field makes the manifest look incomplete and
refuses a sound document. It is a regex over the source rather than a DOM parse, because
this runs in the composer, in a node test and in the import path, and a document that
parsed differently in the browser than it validated in a test is the failure this whole
format is trying not to have.

Then both directions are checked, and **neither is the cosmetic one**:

- **A manifest field with no `[data-field]`** is a block that can never be answered -- it
  takes up points and renders nothing.
- **A `[data-field]` absent from the manifest is worse and quieter:** the student fills it
  in, the frame reports a change, the parent has nothing to map it to, and the answer is
  dropped with no error anywhere. **This is the refusal that closes the `addMfgRow()` hole
  of section 4.5.**

### 10.3 Uniqueness, in three different scopes

| Thing | Unique across | Why |
|---|---|---|
| Module id | the whole manifest | it namespaces its criteria |
| **Block id** | **the whole manifest, header included** | it keys a response row per `(item, student)` |
| `field` | the whole manifest | one input cannot answer two blocks |
| Criterion id | **its module only** | `rubricFromSpec` namespaces it as `<moduleId>-<criterionId>`, so `m1-r2` and `m2-r2` collide with nothing |

The header is walked FIRST, so a module block colliding with an identity field names the
header's block rather than the other way round.

### 10.4 The points arithmetic, three ways

1. **A criterion's declared points are its top level's.** `criterionMax` is the one place
   that is decided; a `points` field disagreeing with the top level is refused, and an
   absent one is refused too.
2. **A module's criteria sum to the module's points.**
3. **The modules sum to the manifest's declared total.**

`criterionIssues` from `assignment-spec.ts` is **CALLED, never mirrored** -- the level
count, the strict descent, the bottom at 0, the top at the maximum, a label and a
descriptor on every level -- so a change to what a leveled criterion means reaches the spec
importer, the rubric builder and this validator in the same commit. What lives in
`manifest.ts` is only what is genuinely this format's: the manifest script tag, the
`field` correspondence, and `short`.

**TWO MESSAGES ARE ORDERED DELIBERATELY, AND THE ORDER IS THE VALUE OF THE CHECK.** Levels
are whole numbers and the bottom is 0, so `[1, 1, 0]` is the only three-level shape a
1-point criterion can take -- which means the strict-descent rule ALWAYS fires on it, and
an author reading "level 2 must be worth less than the level above it" first goes and
rewrites levels that were never the problem. So "worth N but carries M levels, which need
M-1 distinct values above zero" is reported FIRST, in both the TypeScript and the SQL. The
two-level case gets its own sentence for the same reason: it is the shape an author reaches
for most, and it has somewhere else to go (a checkbox block).

## 11. Porting an existing document

The port is **MECHANICAL, NOT A REWRITE**. Every widget, counter, demo and print rule is
left alone. The steps, from the one real port on record (ledger 0128, corrected by 0134):

1. **COPY THE SOURCE. DO NOT EDIT IT.** `src/lib/legacy/assignments/*.html` are documents
   students are working in right now. A defect found in the original is REPORTED and not
   changed. Ledger 0128 and 0134 both md5-verified `idea100-blade-01.html` unchanged at
   the end of the bundle.
2. **AUTHOR THE `idea-manifest` BLOCK** for every module: ids, fields, types, points,
   criteria and levels. Ids in `HTML_ID_RE`, never dotted (section 4.3).
3. **DELETE THE STORAGE LAYER.** `saveToStorage`, `loadFromStorage`, any autosave interval,
   any boot block that reads saved state. `localStorage` throws in an opaque origin.
4. **DELETE THE DOWNLOAD PATH.** Submission stops being a download.
5. **REWIRE IMAGE INPUTS.** A `FileReader` result goes to `idea:image` instead of into a
   local array. Wire the caption and remove controls to `idea:image-caption` and
   `idea:image-remove`.
6. **REWIRE EVERY INPUT TO `idea:change`**, and seed from `idea:state` on `idea:ready`.
7. **ADD `data-field` TO EVERY INPUT THE MANIFEST DECLARES, AND TO NOTHING ELSE.** Both
   directions are refused (section 10.2). A table gets ONE `data-field` on the table, not
   one per cell.
8. **CHECK THE COPY.** No weekdays, no British spellings, anywhere a student reads.
9. **PUT THE RESULT THROUGH `validateHtmlManifest` BEFORE CLAIMING IT PORTS.**

**STEP 9 IS THE ONE THAT WAS SKIPPED, AND IT IS WHY THIS IS A NUMBERED STEP RATHER THAN AN
ASSUMPTION.** `tests/html-assignment-port.test.ts` shipped **twenty-six green assertions**
over the ported Blade fixture, including one asserting "three or four levels, never two",
and never once called `validateHtmlManifest` -- which reports **66 errors** on the same
bytes. A test written from the standard cannot see a conflict with the code, and a test
written from the code cannot see a conflict with the standard. The suite now pins the
charset against `HTML_ID_RE` with a control and puts the fixture through the real
validator.

**THE RUBRIC IS USUALLY THE REAL AUTHORING JOB.** Legacy documents carry FLAT rubrics -- a
criterion and a point value. The Blade port's nineteen criteria and sixty-six levels were
authored top-down from the document's own criterion text, which is the only authority
available: the existing sentence becomes the top level, and each lower level is defined by
what is missing from the one above, per `IDEA_RUBRIC_STANDARDS`. Four levels where the
criterion has room for a real middle distinction; three where a fourth would be invented.

### 11.1 The rubric is generated, at import and at every re-upload

`manifestToRubric(manifest)` produces exactly what `classroom_set_rubric` already accepts.
**It DELEGATES to `rubricFromSpec` rather than mirroring it**, by projecting the manifest
onto the rubric-shaped slice of an `AssignmentSpec`: byte equality with a spec-derived
rubric is then a property of construction rather than a claim a test has to keep re-proving.
**A second implementation flattens the levels, and a rubric imported without them is not
partially imported, it is broken** -- every leveled criterion collapses to a number a
grader has to override to reach.

`applyStagedHtmlAssignment` writes the rubric INSIDE itself rather than leaving it to each
call site, because the rubric is a pure function of the manifest and must be rewritten at
EVERY revision. Left to the callers, a second upload surface would store a new document
beside the OLD document's rubric -- which stores fine, renders fine, and is wrong only on
the grading console.

`stagedRubricAfterManifest` takes the DECISION from `stagedRubricAfterSpec` and the ROWS
from `manifestToRubric`. **A hand-edited rubric is never re-derived.**

**THE GRADING CONSOLE IS HANDED `spec = null`**, which is a ported assignment's normal
state and not a degraded one: `levelShort` answers from rung one for every manifest level,
because the contract requires a `short` and the validator refuses an empty one.

### 12.2 THE OPEN CONFLICT: a 1-point leveled criterion is unrepresentable

**RECORDED HERE, NOT RESOLVED HERE.** The decision is
`docs/decisions/entries/22-a-one-point-leveled-criterion-is-unrepresentable.md`,
`Status: open`.

`IDEA_RUBRIC_STANDARDS` (v1.3, section **Criterion Structure > Rules**) states two rules
that are individually sensible and jointly impossible at 1 point:

- *"Four levels by default. Three is acceptable when a criterion is close to binary and a
  fourth level would be an invented distinction. **Never two:** a two-level criterion is a
  checklist item and belongs in a checklist block instead."*
- *"**Top level equals the criterion maximum. Bottom level is always 0.** No criterion may
  have a floor above zero."*

So a 1-point criterion with three levels needs a middle level strictly between 0 and 1 --
`1 / 0.5 / 0` is its only shape -- and both halves of the HTML-assignment importer refuse
it: `_classroom_check_html_manifest` requires whole points on every level, and both halves
require `top >= levels - 1`. **0195's own apply-time self-check asserts the second rule
deliberately**, constructing a 1-point three-level criterion and raising if the checker
accepts it.

**The smallest three-level criterion is therefore worth 2, and the standard forbids the
two-level criterion that 1 point would otherwise allow. A 1-point criterion has no legal
shape.**

**The three candidate resolutions, stated without a pick:**

- **A. Merge a 1-point criterion into a sibling.** The validator's own message already
  proposes it. Changes no applied migration, no standard rule and no arithmetic. Costs an
  author who genuinely wants five distinct 1-point observations in a 5-point module.
- **B. Permit two levels at 1 point.** Narrowest change; the arithmetic already works.
  Concedes exactly what "never two" was written to prevent.
- **C. Permit half points on a level.** Restores the shape the standard describes and the
  shape ledger 0128 actually authored. Needs a MIGRATION relaxing 0195's integrality
  check, and puts fractional arithmetic into every place a rubric total is summed,
  compared and exported.

Decision entry 22 records a stated preference for A and the count that would change it.
**This specification takes no position.**

### 12.3 Half points: which layer refuses them, precisely

The claim "Postgres accepts a rubric level worth 0.5" is TRUE OF ONE PATH AND FALSE OF THE
OTHER, and the distinction matters to anyone acting on it:

- **`classroom_set_rubric` / `_classroom_check_levels` (0095) ACCEPTS 0.5.** The column is
  `numeric`, `jsonb_typeof(... ) = 'number'` is satisfied, and `2 > 0.5 > 0` descends
  strictly. Measured behaviourally by ledger 0129 against the real RPC. **So the derived
  rubric a ported document writes into is not protected by SQL at all.** The grading
  console's between-levels input is `step="0.5"` on purpose, but that is an OVERRIDE -- a
  grader's considered judgement with a required comment beside it -- and a LEVEL is not
  that: a level's points are what every student who lands on that level receives, for as
  long as the rubric stands, and that reaches FACTS.
- **`_classroom_check_html_manifest` (0195) REFUSES 0.5**, on every level, with
  `(...)::numeric <> floor((...)::numeric)`.

So the no-half-points rule is enforced at MANIFEST IMPORT in both halves, and **is an
AUTHORING rule with no counterpart on the rubric-store path**. `isWholePoints` in
`rubric.ts` is where it lives for `manifestRubricIssues`, and its own comment says so:
*"nothing downstream will refuse it, which is exactly why it has to be refused before the
write."*

**A NOTE ON CITING THE RUBRIC STANDARD.** Decision entry 22 and ledger 0128 both cite it as
"`IDEA_RUBRIC_STANDARDS` 1.3" and "1.2". Those are VERSION numbers, not section numbers --
that document's sections are named, not numbered. Cite it by section name, as this document
does.

Two things no session can do, and until both are done the route answers on any host --
