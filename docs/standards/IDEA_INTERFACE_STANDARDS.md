# IDEA Interface Standards
**Version 2.8 - 2026-08-21**

Governs layout, viewport behavior, role parity, and interaction structure for every IDEA app surface: IDEA Classroom, the digital notebook, the reference reader, the grading console, the portal, and any surface built after this document.

**Relationship to the design system.** `IDEA_Design_System.md` governs color, typography, effects, and themes. It does not govern layout or interaction structure, which is why these rules were missing and why a surface could pass design review and still be unusable on the machine it runs on. That document owns what things look like; this one owns how they are arranged and who sees what.

**Relationship to the verification standard.** `IDEA_VERIFICATION_STANDARDS.md` owns how any claim about a build is proven: harnesses, mutation proof, positive controls, generated sweeps, mock fidelity. Those rules were born here and outgrew the title. Read it alongside this document for interface work, and on its own for anything else.

**Scope exception:** GAUNTLET and VANGUARD carry their own design and layout systems. Inside those products, theirs take precedence.

---

## 1. Desktop Is a First-Class Layout

The IDEA program is run from a desktop computer with a wide screen. Students use a mix. A surface that works only in a narrow column is not finished.

- **Every surface has a layout above 1024px.** Not a widened column: a layout that uses the horizontal axis. Shipping a surface whose widest breakpoint is a phone breakpoint is a defect, not a deferral.
- **Master-detail is the default desktop pattern** for any surface presenting a list of things and the contents of one of them: classroom class page and item, notebook entry list and entry, reference library and document. Persistent navigation pane, detail pane, no full page navigation to move between siblings.
- **The layout responds to selection, not only to viewport.** A master-detail surface with nothing selected gives the full measure to the list and does not render the detail pane at all. A persistent two-column split whose second column holds a placeholder is a layout that spends most of a desktop screen saying nothing, while the content it is hiding sits crushed into the first column. Selecting an item collapses back to the split. The transition is animated so it does not read as a page change, and stays behind `prefers-reduced-motion`.
- **The narrow layout stays the phone layout.** Desktop work adds a breakpoint; it never degrades the single-column stack, which remains the only layout on phones and the fallback everywhere.
- **Page width comes from a shared token, not from the component.** A width hardcoded in a component's own style block is a defect. Where several surfaces legitimately differ (a reading measure versus a console), the differences are named tokens, not scattered literals.
- **A working surface uses the width of the window it is in.** A reading measure is a property of reading surfaces, and a console is not one. Where a surface exists to hold several regions side by side, its width comes from the viewport rather than from a measure token borrowed off a document page. Report the measured content width against the window width; a console holding 1100px of content in a 2500px window is a defect whether or not anything looks broken.
- **A reading measure inside a console is still a reading measure.** Widening a working surface widens its panes, and prose in one of them will set a line nobody can track back to the start of. Cap the prose, not the console: narrowing the whole surface to protect one column hands the width back to nothing. Measure line length inside each pane after any width change, and verify the cap is inert on the narrower surfaces that already sit under it. A console widened from 928px to 1376px produced a 1035px line of instructions, fixed at the paragraph and not at the page.
- **Each pane in a multi-region working surface owns its own scroll.** A page that scrolls as one column re-couples the regions the layout just separated: moving down the roster carries the rubric off screen, and the person scrolls back up to do the thing they scrolled down to do. The page does not scroll; the panes do. Prove it by scrolling one pane to its end and asserting the others did not move and the document did not move.
- **Chrome and content share a width source.** Breadcrumbs, tab bars, and mastheads pinned to a value the content underneath does not use will misalign on every page that differs.
- **Reading material does not sit between a person and their work on every return visit.** Instructions, guidance, prompts, and policy panels open expanded the first time and collapse once the person has started working, with the state remembered per person and per item. The material is always one action from being read again and is never removed, since collapsing is about the second visit and not about the first. Where this shape appears on more than one surface it is one component with one behaviour: an assignment's instructions panel and a notebook check-in's guidance prompt are the same decision, and answering it twice is how the two answers drift apart.
- **A no-scroll guarantee comes from the content fitting, never from a container that clips.** A pane sized to the viewport satisfies every no-scroll measurement by hiding whatever overflows, which is the opposite of the requirement. When the constraint is that something must always be reachable without scrolling, prove it by measuring the document against its own content, not by measuring a container that was told what height to be.
- **A layout constraint holds across every reachable state, not just the one on screen when it was measured.** States arrive later: a warning panel appears, a status strip populates, a disclosure opens, a list grows. Enumerate what can appear and measure each. A no-scroll page measured empty went 135px over the moment logging a fine made a debt panel appear, and nothing about the initial measurement predicted it.
- **Vertical scroll is a cost, not a neutral.** If a desktop user has to scroll to see something that would fit beside what they are already looking at, the layout is wrong.
- **Density is a layout decision, not a taste one, and its floor is the tap target.** A surface can be simultaneously cramped and mostly empty: rows ellipsising inside a card spending an eighth of its width on padding. Audit the vertical rhythm as a set (row height, gap, heading spacing, gutter, card padding) rather than tuning one value, and stop tightening at the point where a row would fall under 44px. Report the before and after numbers.
- **A breakpoint is found by measuring where the layout stops working, not by naming a device width.** State the bar first in terms of what must remain usable, then measure at what width it fails, then put the breakpoint there. A strip that needed three whole tabs visible failed at 40rem on the densest surface, not at the 375px that had been named in the brief. Report the numbers behind the choice. The same applies to a column width: measure the width at which the content stops gaining, not the width that sounds round.
- **Paging through a strip steps by item, never by a fraction of the viewport.** When item widths vary, a fixed-step pager drops items between two grid positions and swaps them between the edges forever. A press lands an item fully in view, and the landing gap is checked against the widest item so a nearly-strip-width item can still fit. This left 7 of 14 tabs permanently unreachable before it was caught.
- **A layout token set inline from a route out-specifies every stylesheet rule.** An inline `style="--x: …"` on a wrapper cannot be widened, narrowed, or overridden by any selector, including a `:has()` rule written specifically to do so. Where two writers need to set the same layout token, both must be stylesheet rules so specificity can decide between them; route-level values pass through a differently-named token that the stylesheet resolves. This shipped once as 960px of chrome sitting over a 1440px split, which is the exact defect the `:has()` rule had been added to fix.
- **A horizontal strip whose item count is not fixed by design must scroll, and must give the person a way to scroll it.** Tab strips, section switchers, filter rails, chip rows: anything whose length depends on content will eventually exceed its container, and the container will usually be narrower than the one it was designed in. The strip scrolls, not the page or the pane. It carries a real control: a visible scrollbar, edge buttons, or both. Wheel and pointer drag both work. The active item is scrolled into view on mount and on change, and the whole strip is reachable by keyboard. An edge fade is a hint that more exists, never the control itself, and selecting an item is never the only way to move.
- **In a persistent pane, state seeded at construction outlives the thing it described.** A component that used to remount on every navigation now does not, so any value initialized once from props keeps naming whatever was open before. Re-derive from the current data rather than seeding, or clamp on change. This shipped as a reference document whose active-section slug came from the previously opened document, hiding every section at once, and it only became reachable when the detail pane became persistent. Expect this shape wherever a pane stops remounting.
- **The `main` landmark follows the content, not the container.** In a responsive split, whichever pane is the content at that viewport carries the landmark. A pane hidden at the current breakpoint must never be the document's only `main`. Verify this at every viewport and route combination, not once.

**Rationale.** Both IDEA Classroom and the notebook were built mobile-first. A 2026-08-16 audit found no media query above 1024px anywhere in the classroom, reference, or notebook surfaces, five distinct hardcoded page widths in the classroom alone (46, 48, 52, 60, and 62rem) with no shared value in the design system or the shared stylesheet, and shell chrome pinned at 60rem above content that is often 46. Nobody noticed because every viewport check had been run at 375px.

## 2. Role Parity

**An instructor's view of student-facing content is the student view plus edit affordances. It is never a different view.**

- The instructor renders the same content, in the same layout, through the same render path as the student. Editing is entered deliberately and applied in place on those same regions.
- **One component, gated by prop.** Two independent implementations of the same content is a defect. When one exists, the fix is consolidation onto one render path, not keeping them in sync. This pattern is already load-bearing in three places in idea-app (`ItemDetail` gated by `canManage` and transports, `NotebookView` gated by `readOnly`, `SpecRenderer` gated by `readonly`); new work widens that seam rather than inventing another.
- **The same rule holds on the server, where the copies are harder to see.** Two normalizers, validators, or projectors that are line-for-line duplicates are not two implementations of a rule; they are one rule with two places to fix it and one place everybody forgets. Where duplication is deliberate, extract the shared logic and declare the real differences as configuration, so a defect found in one is structurally impossible in the other. Finding a bug in the copy nobody was looking at is the cheap version of this lesson.
- **Soft delete creates two populations, and every read declares which one it means.** A filter, count, badge, empty state, or disclosure default over a collection that can hold removed members applies the same liveness rule as the collection's own renderer, and applies it through one shared helper rather than through an inline check per site. The failure is silent and asymmetric: when soft delete is introduced, one predicate gets corrected and the sibling three lines below it does not, so the surface disagrees with itself and the chip promises something the entry does not contain. Sweep the siblings, not the reported line.
- **Gate at the load, not only in the markup.** Withholding the data is the real boundary; hiding the markup is the second layer. Both.
- **Presence of a transport is presence of a control.** Where a component serves several surfaces at different permission levels, pass the capability rather than a role flag: the control renders when its transport was supplied and not otherwise. One component, no role branch, and a surface that forgot to pass a transport fails closed.
- **Attachments are edited where they render**, not in management panels stacked below the content. A deck is edited on the deck; a spec is edited on the rendered material.
- **Instructor-only content lives in a visually distinct inspector** that cannot be mistaken for student-visible content: instructor resources, revision history, publish and schedule state, section targeting, grading affordances.
- **A component with a student-facing half splits by mode; it does not move wholesale.** Before relocating anything into the inspector, check whether students consume part of it. A deck panel carries both a student's open link and an instructor's upload and replace controls; moving the whole component would hide decks from students. Give it a mode and move only the management half. Any list of things to relocate is a proposal to be checked against what students actually read, not an instruction to be executed.

**Rationale.** This is the Cosso constraint applied to the presentation surface. Any instructor operating from the materials alone must never have to ask whether what they are looking at is what students get. It also removes an entire class of drift bug, where a fix lands on one render path and not the other. The notebook shows the cost of the alternative: it shared only two leaf renderers between the student card and the instructor review panel and re-implemented the frame twice, which produced silent drift in title derivation, date formatting, folder rendering, and pin state.

## 3. Preview Parity

**A preview path reads through the same payload as the thing it previews.**

- A "view as student" or equivalent preview that runs its own query will drift from the real read, silently, every time a migration adds a column the preview's payload does not carry.
- Where authorization genuinely requires a separate query or payload function, that function is maintained as part of the same change as the read it mirrors. Adding a field to the real read without adding it to the preview is an incomplete change.
- A preview is not a substitute for parity, and it is not a place where fidelity is optional. It is the surface most likely to be trusted and least likely to be tested.
- **A preview surface accumulates copies, because it is the one nobody opens.** Check it for duplicated chrome and hand-rolled versions of shared components whenever work touches the surface it mirrors. The classroom's view-as notebook was found rendering two mastheads and its own copy of a shared notice, neither reachable from any harness.
- **A preview whose fidelity cannot be proven is removed, not tolerated.** Partial accuracy is the worst of the three available states: a preview known to be wrong gets ignored and still costs maintenance, and a preview believed to be right routes real bug reports to the wrong surface. The test is not whether it looks close, it is whether a test can assert that the preview's output and the real output came from the same read.
- **Where role parity is real, a separate preview is redundant by construction.** If the instructor already renders the student view plus affordances through one component gated by a prop, the honest preview is that same component with the prop flipped, not a second route running a second query. Building a preview is an admission that parity is not real yet; fix the parity instead. And where the difference between two roles is the payload rather than the render, no preview can close it, so none should be built to look as though it has.

**Rationale.** The classroom's view-as preview dropped both `unit_id` and `body_doc`, because its payload function predated the migrations that added them. The result was a preview that showed no unit headers and flattened every bullet list, on any backend, while the real student page rendered both correctly. Two separate production bug reports traced to this one gap, and both were reported as failures of the student page rather than of the preview.

## 4. Creation Completeness

**Everything an item needs is available at creation, on one surface.**

- The create flow exposes the full authoring surface: body, attachments, links, deck, spec, points, due date, grading category, section targeting, scheduling.
- Nothing is deferred to "after the item exists" as a design choice. Where an attachment technically requires a row id, the composer stages it and fires the attach immediately after create, reporting per-attachment failure rather than silently dropping it.
- Where an attachment genuinely cannot be staged (a multi-request ingest job keyed to a row that must exist first), the flow is create-then-attach in one action on one surface, and the reason is documented rather than left to look like an oversight.
- **A new attachable follows the cheapest existing pattern that fits, not the most elaborate one.** An attachment carrying bytes needs an endpoint and a multi-request job; one carrying only JSON needs a single RPC inside the existing staging pass. Copying the heavier pattern because it is the one most recently built adds an endpoint, a job table, and a failure surface that nothing about the payload required.
- Editing the same item later uses the same surface. One authoring surface, two entry points.
- **An unsaved-work guard fires only when work would actually be lost.** A guard that also fires on navigation the form survives teaches people to dismiss it, and then it protects nothing. Exempt the safe paths explicitly and verify that each exemption stays silent.
- **A partial save keeps the form open with what failed still staged.** Closing on partial success discards the exact thing the error message invited the person to retry.

**Rationale.** A create flow that produces an incomplete item forces a create-then-hunt-then-attach cycle for every single post. Multiply by a semester of daily material and the cost is not small.

## 5. Narrow Writes for In-Place Editing

**A field edited in place needs a write scoped to that field.**

- An in-place editor backed by a whole-row replace makes every single-field save only as safe as the client's copy of the entire row, and turns any omitted parameter into a silent field wipe.
- Before building an in-place editor for a region, confirm a narrow write exists for it. If one does not, the write comes first.
- This is a correctness rule, not a performance one. The failure mode is data loss, not latency.

**Rationale.** `classroom_update_item` is a whole-item replace where a null parameter clears the field. The repo has already worked around this several times with narrow RPCs (`classroom_set_published`, `classroom_set_item_unit`, `notebook_edit_note`, `notebook_set_entry_label`), and the one place in-place editing already worked cleanly, the notebook's note thread, works because its write is field-scoped.

## 6. Saved State Is Visible State

**Every surface that persists work shows whether the work is persisted, and says so on the strength of the server's answer.**

- **Four states minimum, always on screen:** unsaved changes present, writing, saved with the clock time of the last successful write, and failed with what to do next. A surface that shows nothing is indistinguishable from a surface that is silently dropping every write.
- **The indicator is a function of the acknowledgement, never of the dispatch or of a timer.** An indicator that flips when the request leaves the client is worse than no indicator, because it is the one signal everyone trusts and it is affirmatively wrong exactly when the write failed.
- **A failed write is reported to the person who wrote the work,** in the surface they wrote it in, not to the console and not only to an error log. Retry is offered, and the content stays in the editor until a write succeeds. A value that failed once and is never re-attempted unless the person happens to edit that field again is lost work with a calm indicator over it.
- **Autosave does not remove the need for an explicit save.** Someone about to close a laptop wants an action they can take and watch complete, and a debounce interval is not that. Both, with one indicator reporting both.
- **A debounce window is an unsaved-work window.** Navigation inside it loses the last edit, so either the guard covers it or the pending write is flushed on the way out. Verify by navigating mid-window and reading the value back.
- **A refusal is not a retryable failure.** Backing off five times against "this is submitted, so edits are locked" spends fifteen seconds arriving at the same answer while showing a surface that looks like it is still trying. Report a refusal once, in the words of the refusal, with no retry offered. Reserve backoff for causes that can change on their own: network, timeout, transient server error.
- **Autosave is not always correct, and where it is not, the state machine still runs.** A write that mints a revision, notifies someone, or is otherwise observable by a third party is not debounced into existence every 800ms; a note thread would fill with versions nobody asked for. Those surfaces save explicitly and still report dirty, writing, saved, and failed through the same indicator, so a person reads one vocabulary everywhere rather than learning which surfaces are honest.
- **A dirty signal reported upward is corrected by whatever owns the state, never only by the component that raised it.** A component that can unmount will be destroyed mid-signal, leaving the parent holding a flag with nothing behind it and a guard that asks forever. And derive the signal from the save state itself rather than from a proxy that clears on a different schedule: a draft cleared before the acknowledgement means the last thing the parent heard was dirty at the exact moment the write succeeded.
- **"There is content here" is not "this has been edited."** A form opened on an existing record carries that record's content from the first frame, so a dirty signal derived from emptiness reports unsaved work before anyone has touched anything. The baseline is the seeded value and dirty is a divergence from it, which makes both questions one comparison against different references so they cannot drift apart. Creating a new record hides this entirely, since the baseline there is empty and the two questions agree, which is why it survives every review.
- **A dirty signal originates in a person's edit, never in the component's own initialization.** Seeding a rich-text editor emits a transaction indistinguishable from typing, so a field wired to the editor's change event marks itself dirty on mount before anyone has touched it. Under an explicit save that shows as a guard prompting on a form nobody edited, which teaches people to dismiss guards. Under autosave it is an unbounded write loop against the database. Compare against the editor's own serialization of the seeded value at mount, and count only a divergence from that as an edit.
- **A busy flag is cleared in a `finally`.** A throw that leaves the flag set disables the controls permanently, which the person experiences as the surface dying rather than as an error they could retry.
- **The state is per surface, not global.** A banner in the shell reading "all changes saved" while one pane holds a failed write is a false negative with a wide blast radius.

**Rationale.** This is student work, produced once, under a deadline, on a school network. The cost of a silent failure is not a bad experience, it is a student who did the assignment and has nothing to show for it, discovered at grading time when there is no way to reconstruct it.

## 7. Content Round-Trips Without Loss

**Whatever the editor lets a person make, every stage after it accepts. Where a stage cannot, the editor never offers the affordance.**

- **An editor never accepts input the pipeline will discard.** The editor's schema, the normalizer's allow list, the storage gate, and the renderer are one contract, not four independent opinions. If nested lists are not carried end to end, the editor does not offer nested lists and does not bind a key to producing them. Silently narrowing content after the person has committed it is the failure mode; refusing the affordance up front is the fix.
- **A drop is never silent.** Where a stage genuinely must reject or alter content, it reports what it changed, to the person, at the moment of the write. A normalizer whose result type has no channel for "changed something" cannot report, and that is a design defect rather than an oversight.
- **Loss is proven absent by a round trip, not by reading the allow lists.** Build one fixture holding a single instance of every construct the editor can produce, at every nesting depth it permits, write it, read it back, compare structurally. Reading four allow lists and concluding they agree is how they came to disagree.
- **Text is never joined across a structural boundary.** Where a normalizer merges adjacent runs, the merge stops at every boundary the source document expressed. Two list items concatenated into one string is not degraded formatting, it is destroyed content.
- **A pipeline that can narrow content keeps the pre-write copy** long enough to put it back. Where revision history exists, normalization runs after the history is written rather than before it; otherwise the history stores only what was already narrowed and is worthless for recovery.

**Rationale.** The notebook's pipeline accepted sub-bullets in the editor, bound Tab to producing them, and concatenated them into unreadable strings on submit. Normalization ran in the route before the RPC, so the first revision in the supersedes chain was already destroyed and no copy survived anywhere on the server. The classroom's normalizer is a line-for-line duplicate and carried the identical defect.

## 8. A Repeated Operation Has a Keyboard Path

**Interaction cost is per repetition times repetitions, and the repetition count is a property of the program, not of the screen.**

- **Count the loop before designing the control.** Five criteria per student, twenty-two students, three sections is 330 selections for one assignment. A control that is pleasant once and costs two seconds is eleven minutes of pointing, and the thing that gets skipped is not the pointing, it is the grading.
- **Any operation performed more than roughly fifty times in a sitting carries a keyboard path covering the entire loop,** including advancing to the next item. A shortcut that selects a value but leaves the person reaching for the mouse to move on has removed the cheap half of the work.
- **Shortcuts never fire while a text input, textarea, or editor has focus,** and the surface makes clear which mode it is in. A grader typing a comment must never discover that a number key set a rubric level.
- **The key map is visible on the surface,** in a legend or an inline hint, not only in a document. An undiscoverable shortcut has the adoption of no shortcut.
- **Focus is visible and is never lost by a state change.** After a selection, focus lands on a defined target chosen deliberately, so the loop runs without hunting for where the cursor went.
- **Moving between items never discards unsaved work silently.** A console that reloads its state from the newly selected row is a data-loss path wearing the clothes of navigation.

## 9. Every Surface Reports Its Own Defects

**A defect-report affordance is present everywhere, mounted once in the shell, never added page by page.**

- **Coverage comes from the shell, not from a checklist.** Placing the control per page guarantees that the page nobody remembered is the page that breaks, and the person who found the bug is the one holding the evidence at the moment it is cheapest to capture.
- **The report captures its own context.** Route, role, section, viewport size, build identifier, and timestamp are collected without the person typing them, because the fields a person has to fill in are the fields that arrive empty. Where the environment cannot supply a build identifier that is a function of the artifact, the report says which weaker identifier it carried rather than presenting it as more than it is.
- **It works signed out,** since a broken sign-in is precisely when a report is most needed and least likely to be possible. A public write path is rate limited.
- **An error page carries one.** A route that has failed is the highest-value place to ask what happened, and a default framework error page rendered outside the app's own chrome carries nothing at all.
- **It is excluded only where it would sit on top of a full-screen presentation or gameplay surface,** and there it relocates into that surface's own menu rather than disappearing. Exclusion by category is a decision that gets recorded here; exclusion by oversight is the thing this rule exists to prevent.
- **Reports land in one place,** filterable by the surface they came from, and exportable in a form that can be handed to whoever is going to fix them.

**Rationale.** The alternative is a defect noticed in class, remembered imperfectly at the end of the day, and described from memory a week later without the route, the role, or the state it happened in.

## 10. Legibility and Focus Visibility

**Contrast is measured against the surface a thing actually composites over, not against the page background.**

- Body text and any text carrying meaning clears 4.5:1 against its real ground. A cell inside a card composites over the card, not over the plate behind it, and those are usually different colors.
- **The ground is the element's own computed background, not the container you believe it sits in.** A control that fills itself composites over its own fill, and measuring it against the card behind it names the right rule while answering the wrong question. A grading console override was recorded at 3.13:1 against the card and was 2.95:1 against the fill the control actually paints, so it shipped under the floor inside a bundle whose report read as clean. Resolve the ground by walking up from the element until an opaque background is found, and report which one you used.
- **Focus visibility is text.** A focus ring is the only thing telling a keyboard user where they are, and it is measured like everything else. A hardcoded ink ring measured 1.02:1 on two of three palettes, meaning keyboard focus was not being drawn at all, and no visual review had ever caught it because nobody was looking at that palette with a keyboard.
- **A component that can be mounted in more than one room does not pin a room's token.** Reuse moves a component onto grounds it was never measured against, and the failure is invisible on the plate it was written for. A link colour chosen for a dark classroom measured 2.00:1 on the notebook's paper; an error colour chosen for the portal measured 3.65:1 on the surface where a person most needs to read it. Read through a room hook with a sensible fallback, and measure on every plate the component can reach rather than on the one it came from.
- **A fill derived from its own ink cannot be fixed by darkening the ink.** `color-mix` of a glyph color into its own background moves both together, so deepening the glyph deepens its ground and the ratio barely moves. Pin the fill explicitly and move only the glyph. Arithmetic predicted a pass here and browser measurement found a fail.
- **Color is never the only signal.** Where a set of states is distinguished by hue, each state also carries a glyph, a shape, or a word. Darkening several hues onto one plate compresses the gamut between them, so a set that clears contrast individually can still be hard to tell apart.
- **A state that means "acted upon" is distinguishable from one that means "not yet looked at."** A surface that offers no way to record approval forces the reviewer to hold that state in their head, which is the actual cost of a review console that feels slow.
- **A boundary that carries meaning is measured; a boundary that decorates is not.** A rule dividing two paragraphs inside one card is decoration and needs no ratio. A rule that is the only thing separating two adjacent interactive rows, the outer edge of a control, or the edge of a card sitting directly on the page plate is doing work, and at 1.2:1 it is not doing it for anyone with reduced acuity. Load-bearing boundaries clear 3:1 against what they sit on. Carry the two as separate tokens so the distinction is made at the point of use rather than argued later: raising one global hairline to satisfy the load-bearing cases draws every decorative line at full strength and turns a tuned surface into a wireframe.
- **Interactive targets clear 44px wherever they can be touched, and never fall below 24px anywhere.** 44px applies at any viewport where the surface is reachable on a phone, and on every student-facing surface at every width. The 24px floor is absolute and applies even to mouse-only instructor consoles, where 44px buys reflow rather than reach. Rounding to reach either floor rounds up; a mechanical sweep that snaps to the nearest token can take a 43px control to 41px and report success.
- **An inline target inside prose is exempt, and expanding it is a defect.** Prose lines sit roughly 24px apart, so a 44px hit area on a link inside a paragraph steals taps from the links above and below it. The floors are about controls that own their space, not about words inside a sentence.

**Rationale.** A token sweep across the notebook found twelve of eighteen grid cell states below 4.5:1, five of them below 3:1 on the default plate, plus a focus ring invisible on two palettes. None of it was visible without measuring, and the surface had shipped and been used.

## 11. Viewport Verification

**Every interface change is verified at both ends of the range before it is called done.**

- Minimum two viewports: a desktop width of at least 1440px and 375px. A pass at one end is not a pass. Where a surface has a third meaningful width, measure it too.
- **Report the measured numbers, not a description of them.** "No overflow at narrow widths" is not a measurement. `scrollWidth 375, clientWidth 375` is.
- The check includes whether anything became unreachable, not only whether anything looks broken. Content that quietly stops being visible at a viewport is the failure mode to watch for.
- Anchored or floating UI (popovers, menus, drawers, tooltips) is checked for off-edge positioning at both ends. This has already caused two shipped defects.
- **Anchored UI is positioned against the viewport, not against its nearest scrolling ancestor.** A tooltip or popover rendered inside a scroll container is clipped by that container, and the clipping is invisible at whatever scroll position the component was built at, which is why it survives review and fails in use. Render it through a portal or position it fixed, flip it when it would cross a viewport edge, and verify it inside a container that actually scrolls. Note that a computed `overflow-x: auto` forces `overflow-y` to `auto` as well, so a horizontally scrolling table clips vertically too, and a column header tip anchored above the first row is the canonical case.
- **Both selection states are separate measurements.** On a master-detail surface, nothing-selected and item-selected are different layouts and each is measured at each width.
- **A frozen transition leaves the pane's own layout at the old value**, not merely its computed style, so a measurement taken mid-transition reports geometry that looks like a broken rule and is not. Disable transitions before measuring.

Everything else about how a claim is proven, including harnesses, mutation proof, positive controls, generated sweeps, and mock fidelity, lives in `IDEA_VERIFICATION_STANDARDS.md`.

**Rationale.** Phase 1 of the classroom rebuild ran every viewport check at 375px, caught two real mobile defects, and shipped a classroom with no desktop layout at all. Single-ended verification produces exactly this result: real bugs found, an entire category missed.

---

## 12. Applying These Rules to Existing Surfaces

These rules are not retroactive demolition orders. When work touches a surface that violates one:

- Bring the touched surface into compliance in that pass if the scope is reasonable.
- If it is not, record the violation in the relevant plan document as an outstanding item with a phase attached. Do not leave it undocumented.
- Never build a new surface out of compliance on the grounds that neighboring surfaces already are.

**When a document and the shipped behaviour disagree about something a person sees every day, that is a question, not a defect.** A document records a decision made once, by someone who has not looked at it since. The behaviour is what has been used, taught with, and relied on for months. Resolving silently toward the document deletes a thing somebody chose to keep, and the deletion arrives as a surprise on a surface they open every morning. Report the disagreement, name both sides, and ask. Resolve toward the document without asking only where nobody could have been relying on the difference.

**A per-instance value declared inline cannot be overridden by anything.** Where a set of things legitimately differ, carry the difference as data the stylesheet keys on, so the shared default stays live, specificity can still decide, and a later pass can change one case without hunting through a registry. An inline style beating a class rule does not read as a conflict; it reads as the class rule being wrong, which is how a shared token spent months as dead code beneath eleven values that were actually painting.
