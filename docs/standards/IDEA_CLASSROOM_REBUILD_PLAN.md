# IDEA Classroom Rebuild Plan
**Version 1.21 - 2026-08-24**
**Status: Phases 1, 2, 4a, 4b-1, 4b-3, 4c-1 and 4d shipped and deployed, plus two passes on the reference tab strip and the export 422 fix. Classroom and notebook run on one shared two-pane shell at one breakpoint, on one visual system, with the split responding to selection. 4e shipped 2026-08-22 across four bundles, with migration 0128 awaiting confirmation of application. 4f, 4g and 4h shipped the same day. **Migrations 0128 and 0129 are applied.** Remaining: 4b-2 (in-place editing, needs narrow write RPCs) and 4c-2 (entry-shell consolidation). **The design-system revision is delivered at 2.1 and no longer owed.** Nothing in 4e through 4h has been exercised against the live project by a signed-in person, which is the standing debt and the largest open risk in this plan.**

Governs the functional and visual rebuild of IDEA Classroom's content creation and presentation surfaces. This document records decisions already made; do not relitigate them in future sessions. Build bundles are cut from this plan plus the audit reports.

---

## Why This Exists

The engine layer (validated specs, derived preflight, generated rubrics, grading console, FACTS export) is sound and is not being rebuilt. The creation surface on top of it was built database-out: an import console for a compiler rather than an authoring tool. The instructor's unit of work is a class day; the system's unit of work was a validated JSON document with a placement plan. Visually, the classroom read cheap and greenwashed. The Phase 0 audit located the cause precisely: not ambient effects (the classroom had almost none), but a green-tinted base palette, the root layout's global scanline overlay bleeding under classroom pages, ~25 components hardcoding spacing and radii instead of consuming tokens, and shared rule blocks copy-pasted across six or more components.

A second cause surfaced in production use on 2026-08-16, after Phases 1 and 2 had shipped: the surfaces were built mobile-first and never gained a breakpoint above 1024px, and the instructor's view of an item had drifted into a stack of management panels. The 2026-08-16 audit found the first claim understated (there is no media query above 1024px anywhere in the classroom, reference, or notebook surfaces, and five distinct hardcoded page widths in the classroom alone) and the second largely already repaired.

A third surfaced in the first week of live student use, 2026-08-18: the digital notebook had been built as a write-once system. An entry could not be edited after saving, deleted, or held as a draft, and the classroom stream carried a day's material and its notebook requirement as two unrelated rows. That produced Phase 4d.

## Locked Decisions

1. **Source of truth: app-native with auto repo export.** The database is the canonical home for classroom content, with in-app revision history. On publish and on each saved revision, the app commits the spec JSON to `pina-hash/idea-app` under `materials/<courseid>/<material>/` via the GitHub API, direct to main, no branches. The repo copy is history and backup, not the working copy. Rationale: Placement existed purely to compensate for the app not being canonical; legacy-as-IDEA-history is preserved by the automatic export.
2. **Assignment authoring: import overhaul now, in-app builder later.** Graded assignments keep full spec authoring in chat because rubric discipline and the Cosso constraint are the point. Delivery becomes one action in the app. A structural in-app builder is Phase 3.
3. **Visual scope: the whole classroom, both roles.** Instructor console and student-facing classroom views, including the reference reader chrome. The deck presentation stage and print `@media` blocks are correct as-is and untouched. GAUNTLET, VANGUARD, home screen, and coin surfaces are out of scope.
4. **Scheduling model: read-time liveness.** `published=false` is a draft; `published=true` with a future `publish_at` is scheduled and invisible to students; `published=true` with `publish_at` null or past is live. No cron, nothing flips at go-live. Enforcement lives in RLS, not app code, because `published` was never an application filter: liveness is one `_classroom_item_live` condition applied at every read.
5. **Rich text: shipped.** The composer is a TipTap rich-text editor (bold, italic, H3/H4, bullet and ordered lists, links) with a server-side normalizer, a SQL structural gate, and a no-`{@html}` renderer, over a dual-column `body_doc`/`body` scheme. Paste lands as plain text and markdown syntax does not convert, which is why delivered post text stays paste-ready plain text.
6. **Attached reference documents no longer hide the item body.** A non-empty body renders above the ReferenceDoc.
7. **Shared classroom CSS lives in one stylesheet,** `src/lib/classroom/classroom.css`, loaded at the classroom layout level. Tokens stay in the design-system files; `app.css` stays import-only.
8. **`first_published_at` keeps its original meaning.** Redefining it as "first became visible" would require the scheduled job this design deliberately avoids. Edit tracking gained one term instead (was the item live when the edit arrived), which for an immediately-posted item reduces to `published`.
9. **Desktop is a first-class layout, not a wide phone.** The classroom, the item page, and the notebook adopt a two-pane master-detail shell above a desktop breakpoint: a persistent navigation pane (units with their items, or notebook entries) and a detail pane that renders the selection without a full page navigation. Below the breakpoint the current single-column stack remains and stays the only layout on phones. **Extended 2026-08-20:** the split also responds to selection, so with nothing selected the navigation takes the full measure and the detail pane does not render. Rationale: these surfaces were built mobile-first and never gained a breakpoint above 1024px, so on the machine the program is actually run from, most of the screen sits empty; the persistent-split form solved half of that and left the other half, measured at 416px of content beside 921px of placeholder. Normative form lives in `IDEA_INTERFACE_STANDARDS.md`.
10. **Instructor view is the student view plus edit affordances.** The instructor item page renders exactly what a student sees, in the same layout, with editing entered deliberately and applied in place on those same regions. Deck and spec are the rendered material, edited where they render, and are attachable at creation rather than only after the item row exists. Instructor-only content (instructor resources, revision history, publish and schedule state, section targeting) lives in a visually distinct inspector that cannot be mistaken for student-visible content. Rationale: parity removes the standing question "is this what they actually see," which is the Cosso constraint applied to the presentation surface. Normative form lives in `IDEA_INTERFACE_STANDARDS.md`.
11. **A preview path reads through the same payload as the thing it previews.** Added 2026-08-16 after the audit found the view-as preview systematically less faithful than the page it mirrors, dropping both `unit_id` and `body_doc` because its payload function predates the migrations that added them. A preview that re-implements the read will drift from it, silently, every time a migration lands. Where a preview must run a different query for authorization reasons, that query is maintained as part of the same change as the read it mirrors, never separately.
12. **A notebook check-in attaches to a classroom item through the posting, and does not become an item kind.** Added 2026-08-20. `notebook_session_postings` carries an `item_id`, keyed `(item_id, section_id)` against `classroom_postings`, which is the grain `notebook_unit_items` already uses; a posting carrying one renders as a block on that item and stops emitting its own stream row, and a posting without one behaves exactly as before, so nothing was backfilled. Three constraints are load-bearing and must not be relitigated. **It is not a `classroom_items` kind**, because that creates a second scoring path beside the existing `classroom_grade_submission` route and the FACTS export that depends on it. **The foreign key is `on delete set null`, never cascade**, because the posting is the check-in's presence in the class and cascading would take students' filed entries with it via 0098's `(session_id, section_id)` key. **The load fails open**: a check-in whose item the reader cannot see reverts to a stream row rather than vanishing, since the alternative is work that is owed and displayed nowhere. Rationale: a day's material and its notebook requirement were two unrelated rows a student had to connect themselves.
13. **The notebook is soft-delete throughout, and every deletion is reversible.** Added 2026-08-20. Entries, photos, and notes each carry a nullable deletion stamp; nothing is ever hard-deleted and no notebook table grants DELETE to `authenticated`. A photograph of a page is the only record of that page, so the recovery path matters more than the storage saved. A student may reverse their own deletion; staff reversal is available for anything staff removed. Deleting a note marks its whole revision chain rather than its head, because marking the head would promote the previous revision and answer reads with the note as it stood before the last edit, silently.
14. **The notebook and the classroom are one visual system.** Added 2026-08-20. The notebook consumes the design system's structural tokens: one type scale, one radius scale, one spacing scale, shared with the classroom. Its three palettes survive as background plates only, because they exist so a student can read a photograph of paper under different lighting, which is a legibility need and not an identity claim; switching a palette changes the plate and nothing else. Only the folder colours and the masthead band remain notebook-specific named tokens.
15. **The notebook's default plate is the classroom's console register, and the standalone dark plate is retired.** Added 2026-08-22. The notebook opens on the same graphite base the classroom opens on, and the separately-authored dark plate that stood beside it is removed rather than kept as a second choice. The remaining plates survive unchanged under decision 14, as background plates for reading a photograph of paper under different lighting. Rationale: decision 14 declared one visual system and then left the notebook shipping its own dark, so a student moving between the classroom and the notebook crossed a seam that carried no meaning. Two darks in one system is a drift surface, not a preference. **A stored choice naming the retired plate resolves to the new default rather than erroring or falling through to a light plate**, since the retirement must not change what a student sees except by making it match the classroom. **The stale key is cleared on read**, not left standing, because a plate id left in a browser silently adopts whatever plate later takes that id.
16. **An instructor's working copy of an assignment lives in its own tables, keyed by block, and never in the student tables.** Added 2026-08-22, decided against the 4e audit. `classroom_instructor_responses` mirrors `classroom_responses` column for column on `(item_id, instructor_email, block_id)`, and `classroom_instructor_keys` carries the designation on the item, one key per item. **The reason is 0090's, unchanged:** 0090 rejected a visibility column on the student tables by name, because one forgotten `and not instructor_only` puts an answer key in front of a student while a wrong table name fails loudly. A separate table means every existing read over `classroom_responses` misses instructor rows by construction, with no filter anywhere that can be forgotten. Per-block rows rather than one document per instructor, because `classroom_save_response`'s body, the engine's autosave granularity, and `SpecRenderer` all transfer unchanged, where a blob needs a second serializer and rewrites everything on every keystroke. **Designation is a fact about the item, not about a row**, which is why it is its own table and not a column on the working copy. **File-upload blocks are outside the v1 boundary** and say so on the surface rather than rendering a control that does nothing; a mirrored files table and a mirrored proxy are a second pass. The three constraints from 4e stand: never a submission, never student-visible, readable as a key by every instructor who can read the item's instructor material, which is the existing `classroom_can_read_instructor_material` gate and therefore the Block 4 gate.
17. **`studentWorkRows` does not invent roster rows, and off-roster work is surfaced rather than dropped.** Added 2026-08-22. `ensure()` appending a row for any email found on a response, submission, or approval put non-roster addresses into the grading roster, the FACTS CSV, the Grades tab counts, and the home feed's to-grade chip, all `active: true` and indistinguishable from a student. This was reachable before any instructor-copy work existed, through `classroom_set_enrollment`'s absent domain check, which is the workaround the 4e request grew out of. Off-roster emails come out of `students` so every downstream count is clean, **and the console reports how many were found**, because a silent drop hides a real enrollment mistake exactly as effectively as it hides an instructor's own row.

18. **A section's managers are never student rows, and enrollment removal is bounded by attached work.** Added 2026-08-24, after an instructor's own account was found rendering as a student row in a live check-in grid, carrying a LEFT badge, dashed cells, and a work count, with no affordance anywhere on the surface to remove it. Decision 17 named this case and closed only half of it: `studentWorkRows` stopped inventing rows, so a row that survives is a real enrollment row, and a real enrollment row has no removal path at all because `classroom_set_enrollment` writes an active flag and nothing else. Two rules follow. **Role decides whether a person renders as a student, not enrollment.** Anyone who can manage the section is excluded from the grading roster, the check-in grid, the FACTS export, the Grades tab counts, and the home feed's to-grade chip, whatever their enrollment row says, and the exclusion is applied once where the roster is built rather than per surface. Rationale: an instructor working their own material is how the material gets tested, and testing it must not cost a permanent row in the gradebook, nor a second definition of "can manage" living beside the authorization gate. **Removal deletes only what is reversible.** An enrollment carrying no responses, submissions, approvals, or filed notebook entries is deleted outright; one carrying work is refused, with the counts named, and deactivation offered in its place, because deleting the enrollment orphans the work rather than removing it and decision 13's reversibility rule does not stop at the notebook's edge. Manager exclusion and the decision 17 off-roster count are reported as two separate lines, since a manager row and a stray address are different mistakes and only one of them is a mistake at all.

## Target End-State: Three Lanes

**Fast lane (seconds). Announcements and simple materials. Shipped in Phase 1.**
In-app rich-text composer, file and link attachments with paste support, creation from the class page with that section pre-checked, post to any combination of sections in one action, draft, and scheduled posting. Chat, JSON, and validators never touch this lane. **Extended in 4d:** a notebook check-in stages in the composer alongside the deck and the spec, so a day's material and its notebook requirement are authored once.

**Middle lane (minutes). Reference documents. Phase 2.**
Content stays chat-drafted. Delivery becomes one flow on the item page: paste spec, inline validation with readable errors, live rendered preview, publish.

**Rigor lane. Graded assignments. Phase 2.**
Spec authoring unchanged in chat. Import uses the same one-shot flow. `SpecImport` and `ReferenceTools` consolidated into one importer differing only in validator and RPC. Revision history is stored in-app; wording fixes become an in-app edit creating a new revision, not a rebuild-and-reattach cycle.

**Creation completeness (Phase 4), corrected 2026-08-16.** A staged spec needs no new mechanism: `SpecImporter` already has a staging mode (`stagingMode = !itemId`, `onstage` callback) that survives with no production caller. **A staged deck was recorded in 1.5 as unreachable. That record was wrong and is void.** The audit's finding was about the HTTP layer, namely that `/api/classroom/deck` rejects a missing `item_id` with 400, that authorization is minted per item, and that ingestion is a four-request begin/files/finish job. All of that is true and none of it blocks staging, because attachments already work exactly this way: they are held as `File[]` in composer state and uploaded after `createItem` returns the id. A deck is the same shape with a different endpoint and a longer job. Creation completeness therefore means what it says: deck and spec are both staged in the composer and applied immediately after the item row exists, with per-attachment failure reporting and retry, and nothing about authoring an item requires a second visit. **A third attachable landed in 4d and followed the spec's pattern rather than the deck's**, since a check-in carries no bytes: one RPC inside the existing `applyStagedExtras` pass, no endpoint, no job.

**Where the composer lives, decided 2026-08-16.** Composing takes the detail pane, not the navigation pane. 4a left it in the pane it had always been in, which after the restructure is roughly 26rem, so a full authoring form was rendering into a sidebar while the detail pane sat empty. Composing is state on the section layout rather than a route, because the composer holds staged `File` objects that a navigation would destroy and layout state survives item navigation while page state does not.

## Visual Direction

Green is demoted from paint to signal. It stays the identity color and hits harder because it is scarce. Full token table, mapping, green budget, effects scope, typography weights, and the engineered-not-hacked test are normative in `IDEA_CLAUDE_DESIGN_STANDARDS.md` 2.0 under Visual Identity. That document governs color, typography, and effects. Layout, viewport, preview parity, role-parity, and legibility rules live in `IDEA_INTERFACE_STANDARDS.md`. How any of it is proven lives in `IDEA_VERIFICATION_ADDENDA.md`.

**Design system revision owed, and no longer blocked.** Phase 4d's token sweep changed what the notebook's palette means: `--nb-*` now aliases the shared structural names at each plate rather than standing beside them, three palettes reduced to background plates, and `--nb-ink-faint` was darkened to clear 4.5:1. Decision 15 changes it again, retiring one plate and moving the default onto the console register. `IDEA_CLAUDE_DESIGN_STANDARDS.md` needs a revision recording both. **The stale-copy block is cleared:** the project-knowledge copy is 2.0 and agrees with what this plan references, so the revision is owed rather than blocked. It is written once the current `--nb-*` values are read out of `src/lib/design-system/`, not from this document's description of them.

**Home screen and app-launcher identity are out of this plan.** Locked decision 3 excludes the home screen and the coin surfaces, and that exclusion stands. Per-app card identity, texture, and mark animation are governed by `IDEA_CLAUDE_DESIGN_STANDARDS.md`, which is where the per-app accent data and its rules belong.

**Item-page defect bundle, cut 2026-08-16, diagnosed by audit the same day.**

1. **Rich-text lists flatten. Resolved: this was defect 5, not a separate defect.** All five layers of the write path are correct: the composer sends `bodyDoc` verbatim, `blocksFrom` in `src/lib/server/classroom-doc.ts` names `bulletList` and `orderedList` explicitly, `_classroom_doc_ok` in `0108` accepts `ul`/`ol`, the column write stores the gated document verbatim, and `ItemBody` emits real `<ul>`/`<li>` with no `{@html}`. The audit offered one remaining mechanism, the degrade ladder at `src/routes/api/classroom/item/+server.ts:124-140`, which drops `p_body_doc` and retries the bare RPC when PostgREST answers `PGRST202`. **That path required an unmigrated backend and was ruled out: `0108` is applied.** The degrade ladder is dead code in practice and is retained only as a guard. With the write path intact, the only surface that could flatten a list was the view-as preview, whose payload carried no `body_doc` at all, and that is where the symptom was observed. Repaired by `0113` together with defect 5. `69bbbbd` separately made the degrade visible (`formattingDropped`, surfaced as a named composer failure) so this class of silent drop cannot recur unnoticed. **Standing correction:** the earlier record that this was write-time collapse was a hypothesis restated as a confirmed root cause, and the "unapplied 0108" diagnosis repeated the same error against an auditor's conditional. Neither was ever checked. See `IDEA_instructions.md` Hard Rules.
2. **Duplicate deck and spec panels. Already repaired in `69bbbbd`; premise now inverted.** `ContentComposer` no longer contains a deck panel or a spec importer, and `DeckStager.svelte` was deleted. What remains true is that the page-level `DeckPanel` and both `SpecImporter` mounts render outside edit mode, which was the earlier resolution and is precisely what locked decision 10 replaces. The v1.4 record that both locations must go is correct; the record that the composer still duplicates them is not.
3. **Chip noise. Closed in `04bbd74`.** The Updated badge suppresses on a null `first_published_at` (`classroom.ts:562`), mirroring the write-side rule. Both "Due No due date" leaks are gated on the date rather than on kind. `GradesPanel`'s separator was flipped from leading to trailing in the same pass, since gating the due segment would otherwise leave a dangling middot when points exist without a deadline.
4. **Green bleed. Closed in `04bbd74`.** `classroom.css` gained `body:has(.cr-root)`, which paints the propagated canvas a `min-height:100vh` wrapper cannot reach; the notebook gained the equivalent plus the `.bg-fx` suppression its own comment had claimed but never implemented. Because `--nb-bg`'s dark and IDEA values are scoped to `.nb-root` and cannot cascade up to `body`, all three palette selectors are mirrored onto `:root:has(...)`. Verified in the browser across light, dark, IDEA, and the OS-default state.
5. **Reclassified, then closed by `0113`. This was a view-as preview fidelity defect, not a unit-grouping defect, and it was also defect 1.** The real student class page groups by unit correctly. There is one `ClassView` for both roles, mounted unconditionally; the units query at `[sectionId]/+page.server.ts:236` has no `canManage` branch; the header row is gated on `bare`, not on role; and `classroom_units` RLS is `using (true)` for all authenticated users. The two real role differences are deliberate: empty units render only for a manager, and the heading is suppressed when a course has authored no units at all. **What was broken is `/classroom/view-as/…`.** Its payload came from `_classroom_item_json` (`0085:1347`), whose key list predated both `0108` and `0111` and therefore carried neither `body_doc` nor `unit_id`, and its class page mounted `ClassView` with no `units` prop at all. Repaired by migration `0113` in `5767bab`. `_classroom_item_json` was recreated with both keys; `classroom_view_as_section` was recreated to return the course's units off the section row the guard already resolved; `classroom_view_as_item` was deliberately not recreated, because it returns the function's result verbatim and therefore picks both keys up for free. The client reads `payload.units ?? []` so the fallback is one unlabeled list rather than an error. `work` remains deliberately excluded, since unlike units it would be the admin's own read rendered under a student's name.

**Why it survived two migrations:** `_classroom_item_json` is a hand-written key list, and `normalizeItemRow` reads `body_doc` and `unit_id` behind an `in`-guard, so an absent key degrades silently instead of erroring. That is the same silent-degrade shape as the API route's `PGRST202` ladder, and it is the reason locked decision 11 exists.

**Export 422 defect. Found in production 2026-08-17, fixed in `af477f1`.** Assignment specs showed "GitHub 422: Reference cannot be updated" with Retry never succeeding, which read to the instructor as a problem with the JSON and blocked interactive assignment use entirely. The cause was not stale captured state: Retry already re-read the head correctly, measured rather than assumed. Each press simply got **one attempt**, and the export is itself a burst writer, since saving a spec, saving a rubric and publishing fire three overlapping exports at one item. Against a branch that moved fifteen times in a day, losing the race twice in a row is routine, and all four presses then failed identically on four different fresh parents. Fixed with a bounded retry loop, four attempts, each re-reading the head, rebasing the tree, re-deciding idempotency against that head, and committing with it as parent, with jittered backoff and no force anywhere. Failure classes are now distinguished in the chip's wording, since a collision worth retrying and a refused write must not read alike, and neither should read like a bad file.

**Why the suite never caught it:** the mock GitHub accepted any ref update, so every test ran against a branch that could not move. Recorded as a rule, now in `IDEA_VERIFICATION_ADDENDA.md`. **Still unknown:** whether `main` carries a branch protection rule, since the protection endpoint returned 401 from that environment. If it does, the failure is the refused class and retrying is not the answer.

**Phase 3: in-app assignment builder.** Structural editing of modules, blocks, and leveled rubrics with live preview; JSON becomes the internal representation with import and export as the escape hatch. Deferred until real-season usage informs it. Deferred alongside it: unifying `sort_order` management with the manage console, importer keyboard flow polish.
