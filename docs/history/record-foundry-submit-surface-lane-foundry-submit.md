## Foundry submit surface (`lane/foundry-submit`)

`/foundry/submit`, `/foundry/mine` and `/foundry/contract`, plus the
client-side normalization that lets a student hand over a zip, a folder or a
single HTML file. No migration: 0130/0131 already had every RPC this needed,
including `build_notes` as a `not null` non-empty column. The gallery, the
public detail view and the review queue are deliberately not here.

### The one-input-shape decision

`foundry-ingest` takes a zip and only a zip. Rather than teach it two more
shapes and re-prove every structural assertion against each,
`src/lib/foundry/normalize.ts` turns the other two into a zip in the browser,
and `src/lib/foundry/zip-write.ts` is the writer -- the deliberate mirror of
`zip.ts`'s reader, using `CompressionStream('deflate-raw')` against the
reader's `DecompressionStream`, so the two halves cannot disagree about the
format. It picks STORED over DEFLATE per entry when deflating would grow the
file, which is the normal case for a PNG or a woff2 and matters against a 25 MB
cap. `tests/foundry-normalize.test.ts` round-trips written archives back
through the REAL reader, including asserting that each entry got the method it
should have.

Two things normalize deliberately does NOT do, both because a second copy of a
rule is the copy that stops matching: it does not strip the wrapper directory
(that is `stripWrapperDirectory` inside `planStructure`, which runs on both
sides), and it does not judge the bundle.

Folder noise is a wider set than zip noise, and the two predicates stay apart.
`isOsNoise` keeps its meaning; `folderNoiseLabel` adds `.git` and
`node_modules`. Folding them together would change what the server does with an
uploaded zip, where a `node_modules` is a student who zipped the wrong folder.

### The browser preflight ran in a browser for the first time

`preflight-browser.ts` had only ever been driven from Deno. It needed **no
changes at all** to run under Vite -- the `.ts` extension imports resolve, the
`DOMParser` injection works, and the whole pipeline produced correct output on
the first drive. What DID need fixing was found by reading its output on
screen rather than by running it:

- **`relativeExample` produced `url="bg.png"` for every CSS refusal.** An
  attribute, offered inside a stylesheet, as the thing to write instead. Fixed
  in the shared module so both sides move: `url("bg.png")` for CSS,
  `src="logo.png"` for HTML. Pinned in a test.
- **The surface printed each message's location twice** -- a chip above the
  sentence, and the sentence already begins with `where(path, line)` -- and the
  copy button prefixed it a third time, so the clipboard carried
  "index.html line 6: index.html line 6 loads a font...". Caught by reading the
  clipboard payload back out of the browser, not by looking at the markup.
- **A duplicated wrapper-stripped note.** `FoundrySubmit` briefly added its own
  sentence beside `planStructure`'s, saying the same thing in different words.
  The harness put the two side by side, which is exactly the divergence this
  lane exists to prevent, committed in the one place nobody was watching.

### Parity between the browser and the server

Guarded structurally rather than by comparing outputs, because there is nothing
to compare: both sides import every scanner, cap and sentence from
`src/lib/foundry/preflight.ts`. `tests/foundry-preflight-parity.test.ts`
asserts the ingest function and the browser preflight declare none of the seven
message producers, that both build their HTML reader from the one
`makeDomHtmlReader` factory, and that neither writes a student-facing sentence
of its own beyond a pinned pair of server-only ones (a missing storage object, a
file that would not decode) -- pinned by exact TEXT, so a third reddens.

**What is NOT proven is the deno-dom parse.** The only real difference between
the two sides is which `DOMParser` is handed to that factory. Running the Edge
Function needs Docker or a Deno runtime and this machine has neither, and no DOM
implementation is resolvable in Node either. So the assertion is that the
difference is CONFINED to that injected parser; whether deno-dom finds the same
references in the same HTML as a browser's parser is untested.

### The build contract

Generated by `foundryBuildContract()` in `preflight.ts` itself, from the
constants the checks read. Rendered at `/foundry/contract` through
`FoundryContract.svelte`, which is a component rather than markup in the route
specifically so the dev harness can mount it -- `/foundry/*` is behind the
signed-in gate and the local project is a placeholder with no session.

### Surfaces

`/foundry/mine` is a caller of `$lib/shell/ClassSplit`, not a second split.
Nothing selected renders no detail pane and the card grid takes the whole
measure with `auto-fit` columns; measured at 1440 it lays 2 cards at 675px each
across a 1408px pane. Selection is a URL parameter, so an app is linkable.

`/foundry/submit` is two columns above 64rem -- what the app IS on the left,
what it CONTAINS on the right -- measured at 622px + 747px across 1393px at
1440. Everything an app needs is staged before the row exists, with two
documented exceptions: the cover (the create RPC has no parameter for it, so it
is uploaded and attached immediately after, with its own failure reported and
not fatal) and the bundle (the multi-request ingest job the standard names).

`build_notes` is the field the whole surface exists to collect. It is required
in the database already; what this lane owns is the FRAMING -- the label asks
which AI tools were used as a matter of course, the placeholder and hint name
real ones, and nothing implies a hand-written answer scores better. A field that
reads like a confession gets blank answers.

### Verified

Both surfaces driven in a real browser through `/dev/foundry-submit`, which
mounts the real components with in-memory transports and runs the REAL browser
preflight as its ingest. All three input shapes end to end; a zip that fails
preflight with three verbatim messages and the send button disabled; a folder
with 8 noise files dropped and reported in three categories; a single HTML file
renamed. Viewport at 1440 and 375, both selection states, 0 controls under 44px,
`scrollWidth === clientWidth` at both ends in every state measured.

One real defect was found by measurement and fixed: four Edit buttons computed
39px because they carried `tap-reach-44`, which is for a control inside a line
of text. They own their cell, so they take `tap-44` and grow.

### NOT verified

- **The real routes were never loaded in a browser.** `/foundry/*` is behind the
  signed-in gate and the local `.env` is a placeholder project with no session,
  so what was driven is the components through the harness. The gate itself was
  verified: all four paths answer 303 to `/` signed out.
- **Nothing has run against a real Supabase project.** No app has been created,
  no zip uploaded to `foundry-uploads`, and `foundry-ingest` has never been
  invoked from this surface. The transports are written against the RPC
  signatures in 0130 and typed, but the round trip is untested.
- **The deno-dom parse**, as above.
- **`scanJs` only scans `.js` files**, so a `fetch` inside an inline `<script>`
  in an HTML file is not flagged on either side. Both sides agree, which is what
  this lane guarantees; widening the scan is a preflight rule change.
