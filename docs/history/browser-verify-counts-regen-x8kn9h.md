One generated block, regenerated by its one writer. Nothing in `src/` moved and
no migration was written. The whole diff is eight lines inside the counts
markers in `tools/browser-verify/README.md`, plus this entry and the ledger
entry that opened the session.

**This branched from `origin/integration` (`fe07200`), not from `main`.** That
is the exception rather than the habit, and the reason is concrete: the counts
block, `tests/derived-numbers.test.ts` and `tools/browser-verify/routes/feedback.mjs`
are all on `integration` and none of them is on `main`. A session starting from
`main` cannot reproduce the failure at all, because two of the three files it
needs do not exist there, and would regenerate the block against a tree missing
the spec that made it stale.

## What was actually wrong, confirmed against the tree rather than assumed

Reproduced before touching anything: `tests/derived-numbers.test.ts` failed 2 of
7, on `agrees with the tree on every static count` and on `passes verifyBlock`.
The tree derived 66 specs, 37 routes and 132 runs; the committed block said 65,
36 and 130. `devPages` (69) and `widths` ([375, 1440]) agreed throughout, which
is the tell that one spec file was the whole difference rather than anything
structural.

The cause was checked in three independent ways rather than inferred from the
symptom:

- `tools/browser-verify/routes/` holds 67 non-`_`-prefixed entries, 66 of which
  are `.mjs` specs (the 67th is the directory's own `README.md`, which the
  derivation does not count). `_shared.mjs` and `_tools` are the two excluded.
- `routes/feedback.mjs` is present on `origin/integration` and absent from
  `origin/main`, which is exactly the asymmetry the failure predicts.
- The block was last written by `859c8d5` at 09:01:09Z; `feedback.mjs` arrived
  in `2d30dcc` at 09:27:20Z on a different branch. The block predates the spec
  by 26 minutes and by one merge, `fe07200`.

**Neither branch was wrong on its own, which is the point worth keeping.** 0005
generated the block correctly from a tree carrying 65 specs. 0006 added a route
spec correctly on a branch where no block existed to regenerate. Only the merged
tree is inconsistent, and only the merged tree can be. That is the class of
failure `integration` exists to expose, and the test 0005 wrote caught it on its
first real merge.

## The block is regenerated, never edited, and the tool enforces that from both ends

`npm run verify:readme` is the only writer. Read from its `main()` and its
argument parser rather than from its prose: it always calls `assembleCounts`,
which needs a measured report, and the only two sources of one are running the
harness (`runHarnessJson`) or `--from <report.json>`. The parser accepts exactly
`--check` and `--from` and nothing else. **So there is no static-only mode**, and
a session without a browser cannot regenerate the block correctly at all. That
is recorded here as an input to a decision that is Mr. Pina's, not as a
complaint about the tool and not as a licence to change it: `readme-counts.mjs`
was read-only to this bundle.

Editing a digit by hand is not a shortcut either, and the test is what makes
that true in both directions. `verifyBlock` re-renders the table from the block's
own `counts:data` line and requires it byte-identical, so a hand-corrected number
reddens on the render check even when the number is right. The suite carries two
permanent positive controls for exactly that, and both passed here, so the four
green assertions are not green vacuously.

## What was measured

A full run in this container, once, with the self-test pass (`--no-selftest` was
not passed: the control count is part of the block, and a block written without
it has a hole where its instrument check should be).

| | before | after |
| --- | --- | --- |
| Route specs | 65 | 66 |
| Distinct routes | 37 (tree) vs 36 (block) | 37 |
| `/dev` page directories | 69 | 69 |
| Route/width runs | 130 | 132 |
| Measurements | 1710 | 1738 |
| Outside threshold | 4 | 4 |
| Wall clock | 312.8s | 304.3s |
| `--selftest` controls | 64 (32 neg, 32 pos), 0 failures | 64 (32 neg, 32 pos), 0 failures |

The four outside-threshold measurements were compared **by identity and not by
count**, because a count alone cannot tell a pre-existing known-red finding from
a new one that replaced it:

- `/dev/pathways` @375 `tap-target` (harness controls)
- `/dev/pathways` @1440 `tap-target` (harness controls)
- `/dev/coins-signedin-1` @375 `horizontal-scroll`
- `/dev/coins` @375 `horizontal-scroll`

The two sets are identical: no finding is new and none was resolved. So the
merged `feedback.mjs` spec contributed 2 runs and 28 measurements and **zero**
findings, and the unchanged `4` in the block is a genuine unchanged 4 rather
than a coincidence hiding a swap.

Two properties of the new block are better than the old one's and are worth
naming because they are what a later reader will check. It records `dirty: false`
where the previous block recorded `(working tree dirty at measurement)`, and it
names commit `6841f4e` — this branch's ledger commit, the tree that was actually
measured. The previous block named `56b3bcd`, which is neither the commit that
wrote it (`859c8d5`) nor a clean tree.

## Verification

- `tests/derived-numbers.test.ts`: 2 of 7 failing before, **7 of 7 passing
  after**, both positive controls among them.
- Full suite: **230 files, 4751 tests, all passing**, which is exactly the shape
  CI run #510 measured (230 files / 4751 tests with 1 file and 2 tests failing).
  `tests/foundry-author-class.test.ts`, flagged as a known flake on the
  enrollment `created_at` precondition and owned by 0009, **passed** in this run
  and was not touched.
- `npm run check`: **0 errors, 37 warnings**, breakdown 31 `state_referenced_locally`
  / 5 `css_unused_selector` / 1 `perf_avoid_nested_class`, over 2814 files. The
  baseline held. `PUBLIC_SUPABASE_URL` and `PUBLIC_SUPABASE_ANON_KEY` were
  exported as placeholders before the sync, per the phantom-error rule.
- The splice was confirmed surgical rather than trusted: the diff is one file,
  8 insertions and 8 deletions, hunks at lines 32, 36, 40, 44 and 54, with the
  markers at 31 and 55 and the file unchanged at 611 lines. Nothing outside the
  markers moved.
- `npm ci` (never `npm install`) left `package-lock.json` byte-identical, per the
  lockfile-reindentation trap.

## Not verified, and deliberately not attempted

- **No Vercel preview check applies.** This bundle changes a README's generated
  block and ships no surface a browser can open, so there is no URL to name.
- **No local Supabase stack was involved.** Ports 54321, 54322, 54421 and 54422
  had no listener and there is no Docker daemon in this container, so no stack
  was running and none was started. `wsl` does not exist here; the documented
  `wsl docker ps` check is a Windows-side instruction and the Linux equivalent
  was run instead.
- **The harness covers `/dev` routes only.** Nothing signed-in was measured, and
  nothing here should be read as covering a real route.
- Two standing limits of the instrument apply to every number above and are
  restated rather than assumed: the harness blocks non-loopback requests, so
  `fonts.googleapis.com` is refused and **all text was measured in the fallback
  stack**; and `prefersReducedMotion` probed `false`, so that path was not
  exercised.
- Nothing outside the three owned files was changed. `readme-counts.mjs`,
  `tests/derived-numbers.test.ts` and every file under `routes/` were read but
  never edited.
